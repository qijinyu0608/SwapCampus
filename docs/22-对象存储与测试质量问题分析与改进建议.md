当前项目已经把 MinIO 和 CI 都纳入了仓库结构与部署脚本，但两者都还没有完全进入“业务闭环和工程闭环”状态。

关键证据：

- `docker-compose.yml` 已定义 MinIO 服务和相关环境变量，见 [docker-compose.yml](/home/th1rt3en/dev/forge/SwapCampus/docker-compose.yml:20) 和 [docker-compose.yml](/home/th1rt3en/dev/forge/SwapCampus/docker-compose.yml:37)
- `ProductImage` 模型已经存在，但发布商品时并没有上传图片逻辑，见 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:125) 与 [backend/src/modules/products/products.service.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/products/products.service.ts:762)
- 当前种子数据和默认图片全部是静态路径 `/images/products/*`，见 [backend/prisma/seed.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/seed.ts:38)
- 后端 `package.json` 没有 MinIO SDK 依赖，见 [backend/package.json](/home/th1rt3en/dev/forge/SwapCampus/backend/package.json:19)
- CI 只覆盖“后端 Jest + 前端 build”，见 [.github/workflows/ci.yml](/home/th1rt3en/dev/forge/SwapCampus/.github/workflows/ci.yml:8)
- 前端 `package.json` 只有 `build`，没有 `test` 脚本，见 [frontend/package.json](/home/th1rt3en/dev/forge/SwapCampus/frontend/package.json:1)

## 2. 对象存储 / 图片上传问题拆解

### 2.1 MinIO 已接入部署层，但未接入业务层

当前 Compose 已经为后端注入了：

- `MINIO_ENDPOINT`
- `MINIO_PORT`
- `MINIO_ACCESS_KEY`
- `MINIO_SECRET_KEY`
- `MINIO_BUCKET`

见 [docker-compose.yml](/home/th1rt3en/dev/forge/SwapCampus/docker-compose.yml:37)。

但代码层没有看到真正的 MinIO SDK 接入，也没有对象上传服务，这说明 MinIO 主要还停留在“环境已备好”的阶段。

### 2.2 商品发布没有图片上传入口

`ProductPublishPage` 目前只有标题、分类、价格、成色、描述、标签，没有文件选择或图片上传表单，见 [frontend/src/pages/ProductPublishPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/ProductPublishPage.tsx:151)。

后端 `createProduct()` 也只创建商品基本信息，不处理图片元数据，见 [backend/src/modules/products/products.service.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/products/products.service.ts:790)。

这说明：

- 图片上传主链路并未完成
- `ProductImage` 表当前更多是为种子和静态展示服务

### 2.3 当前图片来源仍是静态资源，不是对象存储对象

`seed.ts` 里给不同分类商品分配的是固定静态路径 `/images/products/*.jpg|png`，见 [backend/prisma/seed.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/seed.ts:38)。

这意味着：

- 当前商品展示图更像“前端内置素材”
- MinIO 还没有进入真实商品图片流

## 3. 自动化测试与本地开发体验问题拆解

### 3.1 自动化测试覆盖面偏窄

目前后端只有 4 个 `spec` 文件：

- [backend/src/modules/auth/auth.service.spec.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/auth/auth.service.spec.ts:1)
- [backend/src/modules/health/health.controller.spec.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/health/health.controller.spec.ts:1)
- [backend/src/modules/products/products.service.spec.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/products/products.service.spec.ts:1)
- [backend/src/modules/reports/reports.service.spec.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/reports/reports.service.spec.ts:1)

而前端没有测试脚本，也没有实际测试文件入口，见 [frontend/package.json](/home/th1rt3en/dev/forge/SwapCampus/frontend/package.json:1)。

### 3.2 CI 更像“基础检查”，不是完整回归

GitHub Actions 目前只做：

- `backend npm ci && npm test`
- `frontend npm ci && npm run build`

见 [.github/workflows/ci.yml](/home/th1rt3en/dev/forge/SwapCampus/.github/workflows/ci.yml:9)。

这很好，说明项目有最基本的自动化意识；但还不够覆盖：

- API 集成测试
- 数据库联调测试
- 前端页面交互测试
- Docker 启动验收测试

### 3.3 本地开发体验依赖手动安装

根目录 `Makefile` 提供了 `install`、`backend-test`、`frontend-build`，但这些都要求开发者先把本地依赖装起来，见 [Makefile](/home/th1rt3en/dev/forge/SwapCampus/Makefile:3)。

这会带来：

- 本地环境和容器环境可能不一致
- “Docker 能跑，本地测试跑不起来”的割裂
- 新成员接手时上手成本略高

## 4. 影响评估

### 4.1 对答辩演示的影响

影响不致命，因为当前静态图片和 Docker 一键启动已经足够演示。

### 4.2 对后续迭代的影响

如果后续真的要补：

- 用户上传图片
- 多端一致媒体资源
- 回归测试
- 团队协作开发

那这两块会很快成为瓶颈。

## 5. 改进建议

### 5.1 对象存储改造建议

建议按下面顺序补齐：

1. 后端引入 MinIO SDK，新增对象存储服务
2. 启动时自动校验/创建 bucket
3. 新增上传接口，例如 `POST /uploads/products`
4. 前端发布页增加图片选择、预览、上传
5. `createProduct` 支持把上传结果写入 `ProductImage`

建议改造入口：

- `backend/package.json`
- `backend/src/modules/uploads/*` 或 `backend/src/modules/products/*`
- `frontend/src/pages/ProductPublishPage.tsx`
- `frontend/src/services/api.ts`

### 5.2 测试体系改造建议

建议把测试分成 3 层：

1. 服务层单测：继续扩展 Jest
2. API 集成测试：接入测试数据库或容器数据库
3. 前端关键页面 E2E：建议 Playwright

优先补的测试目标：

- 登录/注册
- 发布商品
- 下单与订单状态流转
- 消息发送
- 后台审核

### 5.3 本地开发体验改造建议

建议至少补一个：

- 根目录 workspace 管理
- `npm run test --prefix backend` 与 `npm run build --prefix frontend` 的统一文档
- `devcontainer` 或更明确的本地开发手册
- 一条 `make bootstrap` 同时完成前后端依赖安装

## 6. 推荐实施顺序

1. 补 MinIO SDK 与 bucket 初始化
2. 发布页接图片上传
3. 商品图片写入 `ProductImage`
4. 补前端测试脚本
5. 扩后端测试覆盖
6. 加 API / E2E 回归
