# SwapCampus 校园二手物品交易平台设计说明

## 1. 项目目标
构建一个面向校内师生的校园二手物品交易平台 Web 系统，覆盖用户认证、商品发布、商品检索、交易流程、站内通讯和后台管理 6 个必做模块，并形成完整课程设计交付文档。

## 2. 设计范围
本期只做 Web 端，不做小程序。

包含范围：
- 买家、卖家、管理员 3 类角色
- 学号实名信息录入与审核态展示
- 商品发布、编辑、上下架、多图展示
- 商品搜索、分类筛选、价格/成色/发布时间筛选
- 下单、订单状态流转、确认完成、互评
- 基于 Socket.IO 的站内即时聊天
- 管理员商品审核、举报处理、用户封禁
- Docker Compose 本地一键启动
- Markdown 文档全集

不包含范围：
- 第三方支付
- 真正的学校统一身份认证对接
- 小程序端
- AI 自动定价和推荐系统

## 3. 技术选型
### 3.1 推荐方案
- 前端：React 18 + TypeScript + Vite + React Router + Ant Design
- 后端：NestJS + TypeScript + Prisma
- 数据库：MySQL 8
- 对象存储：MinIO
- 即时通讯：Socket.IO
- 鉴权：JWT
- 测试：Jest、Vitest，后续补 Playwright
- 部署：Docker Compose

### 3.2 选型理由
- 前后端统一 TypeScript，降低课程项目沟通和维护成本。
- NestJS 自带模块化结构，适合对应课程设计的概要设计、详细设计和测试分层。
- Prisma 便于生成清晰的数据模型和 DDL，利于数据库设计文档同步。
- Docker Compose 能直接满足“一键启动”和部署文档要求。

## 4. 备选方案与取舍
### 方案 A：React + NestJS + MySQL + Prisma + Socket.IO
优点：前后端同语言、工程结构清晰、文档和测试容易统一。
缺点：前后端都要维护 Node 生态。

### 方案 B：Vue 3 + NestJS + MySQL
优点：前端开发上手快。
缺点：与当前“全栈 TypeScript + React 生态”相比，没有明显课程收益。

### 方案 C：React + Django + MySQL
优点：后端成熟稳健。
缺点：前后端语言不统一，不符合“尽量全 TS”的目标。

最终采用方案 A。

## 5. 系统架构
系统采用前后端分离三层架构：
- `frontend` 提供用户端和管理端 Web 页面。
- `backend` 提供 REST API、WebSocket 服务、JWT 鉴权和业务逻辑。
- `infra` 提供 MySQL、MinIO 与 Docker Compose 配置。

核心交互流程：
1. 用户通过前端注册/登录，获取 JWT。
2. 前端使用 JWT 调用商品、订单、聊天、管理接口。
3. 商品图片先上传到后端，再由后端写入 MinIO 并保存元数据到 MySQL。
4. 聊天功能通过 Socket.IO 建立会话，消息内容入库，页面实时刷新。
5. 管理员通过后台页面审核商品、处理举报、封禁用户。

## 6. 功能模块拆分
### 6.1 用户体系
- 注册、登录、JWT 鉴权
- 学号、姓名、学院、手机号信息维护
- 实名认证状态展示
- 信用分展示，默认 60 分
- 个人主页展示在售、已售、评价

### 6.2 商品发布
- 标题、描述、价格、分类、标签、成色、图片
- 商品状态：待审核、在售、已售、已下架
- 卖家可编辑自己的商品

### 6.3 商品检索
- 首页商品流
- 关键词搜索
- 分类筛选
- 价格区间、成色、发布时间排序

### 6.4 交易流程
- 买家下单
- 订单状态：待确认、进行中、待互评、已完成、已取消
- 线下面交说明
- 买卖双方互评

### 6.5 站内通讯
- 会话列表
- 文本消息
- 图片消息预留字段
- Socket.IO 实时推送

### 6.6 后台管理
- 商品审核
- 举报处理
- 用户封禁/解封
- 简易数据看板

## 7. 数据模型
计划至少 10 张表：
- `users`
- `student_verifications`
- `products`
- `product_images`
- `favorites`
- `orders`
- `reviews`
- `conversations`
- `messages`
- `reports`

关键关系：
- 一个用户可发布多个商品。
- 一个商品可对应多个图片。
- 一个订单绑定一个商品、一个买家、一个卖家。
- 一个会话关联一个订单或商品上下文。
- 一个会话包含多条消息。
- 一个订单完成后可生成双向评价。

## 9. 非功能要求
- 后端接口响应结构统一。
- 单元测试覆盖率目标不低于 60%。
- 核心接口和聊天流程具备基础错误处理。
- 提供种子数据脚本，生成不少于 200 条商品数据。
- 使用 Docker Compose 一键启动前后端及依赖服务。

## 10. 风险与应对
- 聊天模块复杂：首期只做一对一会话和文本消息，图片消息先保留字段。
- 时间有限：优先完成必做模块主链路，再补后台看板和增强体验。
- 文档工作量大：边开发边维护 Markdown 文档，避免最后补写。

## 11. 验证策略
- 每个核心模块至少具备一个服务层单元测试。
- 关键业务流程通过手工联调验证：登录、发布商品、检索、下单、聊天、审核。
- Compose 启动成功后，以健康检查接口验证后端可用。
