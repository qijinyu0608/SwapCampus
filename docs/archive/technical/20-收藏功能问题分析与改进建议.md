# 收藏功能问题分析与改进建议

## 1. 文档目标

本文档用于回答两个问题：

1. 当前 SwapCampus 的“想要/收藏”功能处于什么状态
2. 如果要把它从演示能力升级为真实产品能力，功能上应该补什么

因此，本文档不只讨论技术实现，也补充收藏功能的业务目标、用户场景、规则边界、页面表现和验收口径，便于后续开发、测试和答辩统一表述。

## 2. 当前状态判断

当前“想要/收藏”功能已经具备前端交互体验，但还没有形成后端持久化闭环，本质上仍是浏览器本地状态。

关键证据：

- 收藏数据直接存入 `localStorage`，见 [frontend/src/services/favorites.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/favorites.ts:12)
- 收藏状态按本地 scope 组织，用户身份也取自前端本地 session，见 [frontend/src/services/favorites.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/favorites.ts:8) 与 [frontend/src/services/session.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/session.ts:39)
- 数据库层其实已经建了 `Favorite` 表，见 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:112)
- README 也明确承认收藏当前以前端本地存储为主，见 [README.md](/home/th1rt3en/dev/forge/SwapCampus/README.md:40)

一句话概括：现在的收藏更像“当前浏览器里的想要清单”，还不是“账号级、可同步、可统计、可治理”的正式功能。

## 3. 收藏功能应承担的业务目标

如果从真实校园二手交易产品来定义，收藏不只是一个心形按钮，而应该承担以下职责：

### 3.1 帮用户沉淀购买意向

用户看到暂时不买、但准备后续比较或联系的商品时，可以先收藏，降低决策成本。

### 3.2 形成个人兴趣资产

收藏列表本质上是用户的长期偏好记录，应支持反复查看、取消、回访和比价，而不是一次性页面状态。

### 3.3 为推荐和热度提供可信信号

收藏通常比浏览更强，比下单更轻，是非常有价值的中间意向信号，适合参与：

- 首页推荐排序
- 相似商品召回
- 类目热度统计
- 商品吸引力分析

### 3.4 为后续运营能力预留基础

如果收藏成为数据库事实，后续还可以自然扩展：

- 收藏排行榜
- 商品受欢迎程度展示
- 卖家侧“多少人想要”反馈
- 管理端数据分析

## 4. 当前问题拆解

### 4.1 收藏不是后端事实状态

`favorites.ts` 中的 `getFavoriteIds()`、`setFavorite()`、`toggleFavorite()` 全部基于浏览器存储工作，见 [frontend/src/services/favorites.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/favorites.ts:31)。

这意味着：

- 换浏览器就丢
- 清缓存就丢
- 换设备不同步
- 后端无法知道用户真实收藏关系

### 4.2 收藏作用域依赖本地 userId

`resolveScope()` 只是把当前本地用户 id 转成字符串作为 key，见 [frontend/src/services/favorites.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/favorites.ts:8)。

这会导致：

- 收藏与真实账号体系绑定不牢
- “同一用户不同会话”的一致性不可保证
- 后续做推荐、统计、运营分析时，收藏信号可信度有限

### 4.3 数据模型已经准备好了，但业务链路没接上

Prisma 模型里已经存在 `Favorite`：

- `User.favorites`，见 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:55)
- `Product.favorites`，见 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:90)
- `Favorite` 模型及唯一约束，见 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:112)

这说明数据库设计已经具备落地条件，但接口和前端状态管理还停留在演示实现。

### 4.4 收藏能力和推荐能力分裂

项目里已经有行为埋点封装，收藏会形成 `FAVORITE` / `UNFAVORITE` 信号，但收藏主状态并没有依赖后端真实数据，见 [README.md](/home/th1rt3en/dev/forge/SwapCampus/README.md:21)。

结果就是：

- 推荐链路可能能“感知收藏行为”
- 但业务主状态并不以数据库为准
- 以后容易出现“推荐说你收藏过，但收藏页没有”的口径不一致

### 4.5 收藏功能的页面价值还没有完全展开

当前收藏更多是“能点”，但还没有形成完整页面能力。一个成熟的收藏功能通常至少要解决：

- 我收藏了什么
- 这些商品现在还能不能买
- 哪些商品已经卖掉或下架
- 我能不能从收藏列表直接联系卖家、下单、取消收藏
- 收藏记录是否支持排序、筛选和状态区分

这些功能定义目前在文档中还不够完整。

## 5. 功能上建议补齐的内容

### 5.1 功能定位

建议统一口径：

- “收藏”用于表达持续关注意向
- “想要”可以作为前端文案层面的友好表达
- 后端能力、数据库模型、接口命名统一使用 `favorite`

这样既保留校园二手平台更自然的“想要”语义，也能保持工程命名稳定。

### 5.2 目标用户与核心场景

收藏功能至少覆盖以下场景：

1. 用户浏览首页商品流时，快速标记感兴趣商品
2. 用户进入商品详情页后，先收藏再决定是否联系卖家
3. 用户在收藏页集中比较价格、成色和卖家信用
4. 用户回访曾经感兴趣但尚未下单的商品
5. 用户发现商品已售出或下架后，及时清理收藏列表

### 5.3 收藏列表页应具备的能力

建议收藏页从“简单商品列表”升级为“个人意向池”，至少支持：

- 展示商品封面、标题、价格、分类、成色、卖家信息
- 展示商品当前状态：在售、已售、已下架、审核中
- 展示收藏时间，便于用户判断新旧程度
- 支持取消收藏
- 支持跳转商品详情
- 支持直接联系卖家
- 对失效商品提供弱化样式或单独分组

可选增强：

- 按收藏时间排序
- 按价格区间筛选
- 仅看在售商品
- 批量取消收藏

### 5.4 商品卡片与详情页应具备的能力

首页卡片和详情页建议统一支持以下表现：

- 已收藏状态高亮显示
- 收藏操作后即时反馈
- 展示商品收藏数
- 登录用户可看到“我是否已收藏”
- 商品失效后禁止新增收藏，或给出不可收藏提示

详情页建议补充三个清晰动作：

- 收藏
- 联系卖家
- 下单或进入交易流程

这样收藏才会成为交易决策中的中间动作，而不是孤立动作。

### 5.5 收藏的业务规则边界

建议在文档中明确以下规则：

1. 只有登录用户才能产生正式收藏关系
2. 游客可保留本地临时想要，但不计入后端收藏事实
3. 用户不能收藏自己发布的商品
4. 已删除、已售、已下架或审核未通过商品应限制收藏能力
5. 同一用户对同一商品只能存在一条收藏记录
6. 取消收藏后应同步更新商品收藏数与个人收藏列表

其中第 2 条很重要，因为它可以兼顾当前演示体验和后续正式实现：

- 游客仍可体验前端“想要”
- 登录用户进入正式收藏体系
- 登录后可以考虑把游客本地收藏迁移到账户收藏

### 5.6 收藏与交易链路的协同

收藏不应独立存在，建议和交易流程形成联动：

- 商品被收藏后，用户可从收藏页直接发起联系
- 商品成交后，收藏它的用户在列表中看到“已售出”
- 已购买该商品后，可自动从收藏列表隐藏，或转入“已成交记录”
- 若商品重新上架，可恢复正常展示

这样收藏页才不是死页面，而是交易漏斗的一部分。

### 5.7 收藏与推荐链路的协同

建议把收藏定义为强意向信号，并在文档中明确其优先级高于普通浏览：

- 浏览：弱兴趣
- 收藏：中强兴趣
- 联系卖家：更强兴趣
- 下单：最强兴趣

推荐系统后续可按该强弱关系加权，避免“点开看了一眼”和“主动收藏”的权重完全一样。

## 6. 影响评估

### 6.1 用户体验层面

从演示角度看已经够用；从真实产品体验看，收藏仍是脆弱状态。

当前不足主要体现在：

- 用户不能跨设备延续意向
- 收藏页缺少状态治理
- 收藏和下单、联系之间联动不强

### 6.2 数据可信度层面

收藏通常是推荐、热度、转化分析的重要信号。如果它只存在本地：

- 无法做全站收藏榜
- 无法做跨端同步
- 无法做管理员侧统计
- 无法和订单、浏览、联系行为形成统一画像

### 6.3 答辩与文档一致性层面

如果后续老师追问“收藏是如何设计的”，只回答“本地存一下”会显得功能定义偏浅。  
补齐功能目标、规则边界和扩展路径后，这个模块更像一个完整的产品能力，而不是一个页面按钮。

## 7. 改进建议

### 7.1 第一阶段：先补齐最小可用后端接口

建议补三个核心接口：

1. `GET /favorites`
2. `POST /favorites/:productId`
3. `DELETE /favorites/:productId`

接口返回中建议直接包含：

- 商品基础信息
- 当前收藏状态
- 收藏时间
- 商品当前状态
- 收藏总数

对应后端建议新增：

- `backend/src/modules/favorites/favorites.controller.ts`
- `backend/src/modules/favorites/favorites.service.ts`

长期更建议独立成模块，而不是混在 `users` 或 `products` 模块中。

### 7.2 第二阶段：前端改为“后端为准，本地为缓存”

建议把 `favorites.ts` 从“主状态存储器”改成“轻缓存工具”：

- 首屏从后端拉收藏列表
- 点赞/取消收藏时先调用接口
- 成功后再更新本地缓存和 UI
- 请求失败时回滚 optimistic 状态

这样改完后，`localStorage` 仍然有价值，但只是为了：

- 减少首屏闪烁
- 做弱离线体验
- 兼容游客临时想要

### 7.3 第三阶段：统一详情页、列表页和收藏页口径

当前商品详情里已经有 `favoriteCount` 这类字段类型定义，见 [frontend/src/services/api.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/api.ts:55)。

建议服务端统一补齐：

- 收藏总数
- 当前用户是否已收藏
- 收藏时间
- 商品当前可交易状态

这样首页卡片、详情页、收藏页就能统一口径，避免不同页面展示冲突。

### 7.4 第四阶段：把收藏做成可治理的页面能力

建议收藏页增加最少一层状态治理：

- 在售商品默认优先展示
- 已售和已下架商品单独展示或弱化展示
- 支持“一键清理失效收藏”

这类能力实现成本不高，但会显著提升收藏页的实用性。

### 7.5 第五阶段：让推荐真正消费收藏事实

当 `Favorite` 表启用后，推荐模块应优先消费数据库事实收藏，而不是只消费前端行为事件。

建议目标：

- 收藏行为写入 `Favorite`
- 同时写入行为事件表
- 推荐召回优先用持久化收藏 + 浏览 + 联系 + 下单联合建模

## 8. 推荐实施顺序

1. 后端新增收藏接口
2. 前端收藏按钮改为调接口
3. 收藏页改为从接口拉取并展示收藏时间、商品状态
4. 商品详情页补“是否已收藏”和收藏总数
5. 补收藏页筛选、失效状态、快捷联系能力
6. 推荐模块改为消费数据库收藏事实

## 9. 建议验收口径

收藏功能完成后，建议至少按以下标准验收：

1. 同一用户在不同浏览器或设备登录后，收藏列表一致
2. 收藏和取消收藏可实时反映到详情页与列表页
3. 商品下架或售出后，收藏页能展示对应状态
4. 收藏页可以直接进入详情或联系卖家
5. 后端数据库能查询到真实收藏关系
6. 推荐与统计模块能够读取收藏事实数据

## 10. 可用于答辩的结论表述

可以用下面这段话概括当前问题与改进方向：

1. 当前系统已经具备收藏交互和想要页展示能力，但主状态仍以前端本地存储为主
2. 数据库层已预留 `Favorite` 模型，说明系统具备升级为正式收藏能力的基础
3. 后续应把收藏升级为账号级持久化能力，并统一接入商品详情、收藏列表、推荐排序和统计分析
4. 收藏功能的目标不只是“点亮一个按钮”，而是沉淀用户意向、辅助交易决策、增强推荐和支撑运营分析
