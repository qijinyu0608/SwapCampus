# 校园服务双向供需与时效容量重构方案

## 1. 文档目标

本文档用于给校园服务模块下一轮重构提供单独的设计基线，重点解决以下问题：

1. 当前模型只自然支持“我发布任务，别人来接单”
2. 不能干净表达“我要购买服务，别人来为我提供服务”
3. 旧单向任务模型只能绑定单一参与关系，无法承接多次成交、数量上限和连续供给
4. 当前只有流程状态，没有统一的时效结束和容量规则
5. 会话、个人中心、后台治理都默认围绕“单任务单接单人”展开

本文档不直接修改代码，而是作为后续数据库迁移、接口改造和页面重构的统一依据。

补充说明：当前仓库已按本文方案完成主链路落地，后端与前端均已统一到 `CampusServiceListing / CampusServiceOrder / participant` 语义，会话也已统一绑定到 `campusServiceOrderId`。

## 2. 重构结论

校园服务应从“单向任务流”改为“双向服务市场”，按发布意图拆成两条主线：

- `REQUEST`：我要购买服务
- `OFFER`：我要接单挣钱

在这个前提下，旧单向任务模型不再适合作为唯一核心实体，建议拆为两层：

1. `CampusServiceListing`
   表示一条发布内容，负责展示、筛选、时效和容量控制
2. `CampusServiceOrder`
   表示一次具体成交或预约，负责参与双方、状态流转、会话和完成确认

这样可以同时支持：

- 我发布需求，别人来接
- 我发布服务，别人来约
- 一条供给在一段时间内持续有效
- 一条供给或招募设置总数量上限
- 一条供给设置同时进行中的上限
- 到期自动结束，但已成交的服务单继续履约

## 3. 用户视角的产品结构

### 3.1 市场首页

校园服务列表页先按“方向”拆分，再按“类别”筛选：

- 页签一：`我要购买服务`
- 页签二：`我要接单挣钱`

两条页签共享同一套类别体系，但卡片文案和动作不同：

- `REQUEST`
  - 文案偏“需求 / 招募 / 酬谢 / 截止时间”
  - 主动作是“接单”或“应征”
- `OFFER`
  - 文案偏“服务 / 报价 / 可预约时间 / 剩余名额”
  - 主动作是“预约”或“下单”

### 3.2 发布页

发布流程建议改成先选方向，再填具体内容：

1. 选择发布方向
   - 我要购买服务
   - 我要接单挣钱
2. 选择服务模式
   - `ONE_TIME`：一次性
   - `REUSABLE`：在有效期内可重复成交
3. 填写基础信息
   - 标题
   - 类别
   - 描述
   - 金额
   - 地点 / 区域 / 路线
4. 设置时效
   - 生效时间
   - 截止时间
5. 设置容量
   - 总数量上限
   - 同时进行中上限
6. 设置成交方式
   - 自动确认
   - 需发布者确认

### 3.3 个人中心

个人中心不应只保留“我发布的校园服务”，而应拆成四个视角：

- 我发布的需求
- 我发布的服务
- 我接的单
- 我预约的服务

每个视角下再按状态分组：

- 待确认
- 进行中
- 待完成确认
- 已结束

## 4. 领域模型设计

### 4.1 发布内容实体 `CampusServiceListing`

`CampusServiceListing` 负责承载一条可被浏览、筛选和成交的校园服务发布内容。

建议核心字段如下：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `ownerId` | 发布者 ID，统一替代当前 `publisherId` |
| `intent` | `REQUEST / OFFER` |
| `pattern` | `ONE_TIME / REUSABLE` |
| `category` | 服务类别 |
| `title` | 标题 |
| `description` | 描述 |
| `priceMode` | `FIXED / NEGOTIABLE / FREE` |
| `amount` | 固定金额，允许为空 |
| `locationMode` | `ONLINE / ON_SITE / DELIVERY / FLEXIBLE` |
| `locationNote` | 地点说明 |
| `routeFrom` | 可选，路线型服务的起点 |
| `routeTo` | 可选，路线型服务的终点 |
| `validFromAt` | 生效时间，默认 `now()` |
| `validUntilAt` | 截止时间，必填 |
| `status` | 发布状态 |
| `endReason` | 结束原因 |
| `maxTotalOrders` | 总成交上限，空表示不限制 |
| `maxConcurrentOrders` | 同时进行中上限，空表示不限制 |
| `autoConfirm` | 是否自动确认成交 |
| `contactPreference` | 联系偏好 |
| `fulfillmentMode` | 交付方式 |
| `createdAt / updatedAt` | 时间戳 |

设计要点：

- `ownerId` 是中性命名，不再假定发布者一定是“需求方”
- `intent` 决定这条发布内容的业务方向
- `pattern` 决定它是一次性单子，还是有效期内可反复成交
- 容量控制不再依赖单一参与者字段
- 列表和详情都围绕 `Listing` 展示，而不是围绕一次具体成交展示

### 4.2 成交实体 `CampusServiceOrder`

`CampusServiceOrder` 表示一次具体的接单、预约或撮合结果。

建议核心字段如下：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `listingId` | 关联的发布内容 |
| `requesterId` | 需求方用户 ID |
| `providerId` | 服务方用户 ID |
| `status` | 成交状态 |
| `applyMessage` | 初次接单 / 预约留言 |
| `finalAmount` | 最终成交金额，允许覆盖列表金额 |
| `confirmedAt` | 确认时间 |
| `completedAt` | 完成时间 |
| `canceledAt` | 取消时间 |
| `cancelReason` | 取消原因 |
| `expiredAt` | 订单超时失效时间 |
| `createdAt / updatedAt` | 时间戳 |

角色归一规则：

- 当 `listing.intent = REQUEST` 时
  - `ownerId = requesterId`
  - 响应者成为 `providerId`
- 当 `listing.intent = OFFER` 时
  - `ownerId = providerId`
  - 预约者成为 `requesterId`

这个归一方式非常重要，它避免了后续所有逻辑都去判断“当前发布者到底是需求方还是服务方”。

### 4.3 会话实体

旧会话模型如果直接绑定发布内容，一条发布只支持一条会话，这不适合双向市场。

建议改为：

- `Conversation.campusServiceOrderId`

规则如下：

- 一条 `CampusServiceOrder` 对应一条会话
- 发布内容本身不直接绑定唯一会话
- 同一条 `Listing` 可以有多条 `Order`，也就可以有多条独立会话

这样才能支持：

- 我发布一项持续服务，同时和多个预约者分别沟通
- 我发布一项招募，同时和多个候选接单人分别沟通

## 5. 枚举设计

### 5.1 发布方向

```text
CampusServiceIntent
- REQUEST
- OFFER
```

### 5.2 发布模式

```text
CampusServicePattern
- ONE_TIME
- REUSABLE
```

语义建议：

- `ONE_TIME`
  - 面向一次性任务、一次性招募、一次性预约
  - 默认总数量上限为 1，或由发布者显式设置为多名额
- `REUSABLE`
  - 面向一段时间内持续有效的供给或招募
  - 允许多次成交

### 5.3 发布状态

```text
CampusServiceListingStatus
- OPEN
- BUSY
- PAUSED
- ENDED
- CANCELED
```

语义建议：

- `OPEN`
  - 可继续接单 / 预约
- `BUSY`
  - 当前同时进行中的服务单达到上限，暂不可新增
  - 不是最终态，后续可自动恢复 `OPEN`
- `PAUSED`
  - 发布者手动暂停接新单
- `ENDED`
  - 正常结束态，用户侧展示为“已结束”
- `CANCELED`
  - 管理员关闭或违规撤销

### 5.4 结束原因

```text
CampusServiceListingEndReason
- EXPIRED
- QUOTA_REACHED
- MANUAL_END
- ADMIN_CLOSE
```

设计约定：

- 超时结束统一写入 `ENDED + EXPIRED`
- 达到总数量上限统一写入 `ENDED + QUOTA_REACHED`
- 发布者主动结束统一写入 `ENDED + MANUAL_END`

### 5.5 成交状态

```text
CampusServiceOrderStatus
- PENDING_CONFIRMATION
- CONFIRMED
- WAITING_COMPLETE_CONFIRM
- COMPLETED
- REJECTED
- CANCELED
- EXPIRED
```

语义建议：

- `PENDING_CONFIRMATION`
  - 对方已发起接单或预约，等待发布者确认
- `CONFIRMED`
  - 已确认，可进入履约
- `WAITING_COMPLETE_CONFIRM`
  - 一方标记完成，等待另一方确认
- `COMPLETED`
  - 双方完成闭环
- `REJECTED`
  - 发布者拒绝本次预约或应征
- `CANCELED`
  - 任一方取消
- `EXPIRED`
  - 长时间未确认或超出订单有效期

## 6. 时效与容量规则

这是本次设计的核心。

### 6.1 时效规则

每条 `Listing` 必须具备统一时效：

- `validFromAt`
- `validUntilAt`

建议约束：

- `validUntilAt` 必须晚于 `validFromAt`
- 最短有效期建议不低于 30 分钟
- 最长有效期建议不超过 30 天
- 已结束的发布内容允许“延长时间并重新开放”，但必须显式操作，不能被系统静默复活

超时行为：

1. 定时任务按固定频率扫描
2. 将 `OPEN / BUSY / PAUSED` 且 `validUntilAt <= now` 的记录改为 `ENDED`
3. `endReason` 写入 `EXPIRED`
4. 所有 `PENDING_CONFIRMATION` 的关联 `Order` 改为 `EXPIRED`
5. 已 `CONFIRMED` 的 `Order` 不自动取消，允许继续履约直至完成或取消

这样可以满足你的要求：

- 列表本身到时结束
- 已经谈妥或正在做的服务单不被硬中断

### 6.2 容量规则

建议把容量拆成两个维度：

1. `maxTotalOrders`
   - 整个有效期内最多成交多少单
   - 适合“这周最多接 10 单”“本次招募最多 3 人”
2. `maxConcurrentOrders`
   - 同一时刻最多允许多少个进行中的服务单
   - 适合“我一次最多同时接 2 单”

默认策略建议：

- `REQUEST + ONE_TIME`
  - `maxTotalOrders = 1`
  - `maxConcurrentOrders = 1`
- `REQUEST + REUSABLE`
  - 可由发布者自定义总名额和同时进行中名额
- `OFFER + ONE_TIME`
  - `maxTotalOrders = 1`
  - `maxConcurrentOrders = 1`
- `OFFER + REUSABLE`
  - 常见为 `maxTotalOrders = null`
  - `maxConcurrentOrders` 由提供者自定义

状态切换规则建议：

- 当前进行中的服务单达到 `maxConcurrentOrders`
  - 切换到 `BUSY`
- 有服务单完成或取消，且仍未到期
  - 从 `BUSY` 恢复到 `OPEN`
- 累计成交达到 `maxTotalOrders`
  - 切换到 `ENDED`
  - `endReason = QUOTA_REACHED`

这里建议采用保守口径：

- `maxTotalOrders` 一旦达成，即认为本轮额度已经用完
- 即使后续有人取消，也不自动重新开放
- 若发布者想继续开放，应手动“延长并重开”

这样规则更稳定，也更容易向用户解释。

### 6.3 自动确认规则

建议引入 `autoConfirm`：

- `true`
  - 对方发起接单或预约后，系统直接创建 `CONFIRMED` 的 `Order`
- `false`
  - 对方发起后先进入 `PENDING_CONFIRMATION`
  - 由发布者手动确认或拒绝

默认策略建议：

- `REQUEST + ONE_TIME` 默认 `false`
  - 避免需求方被陌生人瞬时锁单
- `OFFER + REUSABLE` 默认 `true`
  - 适合标准化、低风险、连续供给服务

## 7. 分类重构建议

当前分类 `ERRAND / AGENCY / GROUP_BUY / HELP` 过于粗糙，尤其 `HELP` 过大，不利于双向市场筛选。

建议改成“方向和类别分离”的结构：

- 方向是 `intent`
- 类别是 `category`

建议一级类目如下：

| 类目 | 说明 |
| --- | --- |
| `ERRAND` | 跑腿配送、取送物品 |
| `AGENCY` | 代办代取、排队代办 |
| `GROUP_BUY` | 拼单团购、校内代下单 |
| `MOVING` | 搬运、宿舍协助、物品转运 |
| `TUTORING` | 学习辅导、资料帮助、答疑 |
| `SKILL` | 设计、摄影、剪辑、技术支持 |
| `REPAIR` | 维修、装机、调试、安装 |
| `EVENT` | 活动协助、临时人手、招募合作 |
| `OTHER` | 其他无法稳定归类场景 |

补充建议：

- `GROUP_BUY` 保留，但应只作为类目，不应继续绑定“单接单人”模型
- 当前 `HELP` 应拆散到 `MOVING / TUTORING / SKILL / EVENT`
- 路线型字段只在 `ERRAND / AGENCY / MOVING` 等类目中重点展示

## 8. 接口层改造建议

### 8.1 发布内容接口

建议保留 `/campus-services` 作为资源前缀，但内部语义改为 `Listing`：

- `GET /campus-services`
  - 支持 `intent / category / status / keyword / page / pageSize`
- `GET /campus-services/:id`
  - 获取单条发布内容详情
- `POST /campus-services`
  - 创建发布内容
- `PATCH /campus-services/:id`
  - 编辑发布内容
- `POST /campus-services/:id/pause`
  - 暂停接新单
- `POST /campus-services/:id/reopen`
  - 重新开放
- `POST /campus-services/:id/end`
  - 手动结束

### 8.2 成交接口

- `GET /campus-service-orders`
  - 按当前用户身份查询“我接的 / 我预约的 / 待我确认的”
- `POST /campus-services/:id/orders`
  - 针对某条发布内容发起接单或预约
- `POST /campus-service-orders/:id/confirm`
  - 确认成交
- `POST /campus-service-orders/:id/reject`
  - 拒绝成交
- `POST /campus-service-orders/:id/complete`
  - 提交完成
- `POST /campus-service-orders/:id/confirm-complete`
  - 对方确认完成
- `POST /campus-service-orders/:id/cancel`
  - 取消服务单

设计原则：

- 列表详情接口只处理“发布内容”
- 接单预约、完成取消都作用于“服务单”
- 不再把“接单人”直接写回发布内容主表

当前落地补充：

- 仓库内已实现 `PATCH /campus-services/:id`
- 已支持发布者修改有效期、容量、金额与说明
- 对于 `MANUAL_END` 的发布，若延长 `validUntilAt` 到未来时间，可在编辑时直接恢复开放

## 9. 页面与交互改造建议

### 9.1 列表页

列表页每张卡片建议新增以下信息：

- 方向标签：我要购买服务 / 我要接单挣钱
- 有效期截止时间
- 当前状态：可预约 / 忙碌 / 已结束
- 容量提示：剩余名额 / 同时上限

### 9.2 详情页

详情页新增两块信息：

1. 有效期与容量信息
   - 生效时间
   - 截止时间
   - 总额度
   - 同时进行中上限
2. 当前发布内容的成交摘要
   - 已确认多少单
   - 进行中多少单
   - 已完成多少单

### 9.3 个人中心

个人中心新增两个维度：

- 发布维度
  - 我发布的需求
  - 我发布的服务
- 参与维度
  - 我接的单
  - 我预约的服务

不要再只用“我发布的校园服务”承接全部场景。

## 10. 数据迁移建议

从旧单向任务模型迁移时，建议采用以下映射：

### 10.1 主表迁移

旧发布记录 `-> CampusServiceListing`

字段迁移建议：

- `publisherId -> ownerId`
- `category -> category`
- `title -> title`
- `description -> description`
- `reward -> amount`
- `deadlineLabel`
  - 不再作为唯一时间字段
  - 需要拆成真实时间字段 `validUntilAt`
- `matchedAt / completedAt / canceledAt`
  - 不再作为发布内容主状态依据
  - 新逻辑下应主要下沉到 `CampusServiceOrder`

### 10.2 接单信息迁移

若旧记录已经存在明确参与方：

- 补生成一条 `CampusServiceOrder`
- 其中：
  - `requesterId / providerId` 根据 `intent` 反推
  - `status` 由旧流程状态映射

### 10.3 会话迁移

- 旧会话绑定关系
  - 迁移到 `Conversation.campusServiceOrderId`
- 若一条旧任务已有已匹配接单人
  - 将旧会话绑定到迁移出的唯一那条 `Order`

## 11. 实施顺序建议

建议按下面顺序推进，风险最低：

1. 数据库层
   - 新增 `CampusServiceListing`
   - 新增 `CampusServiceOrder`
   - 为 `Conversation` 增加 `campusServiceOrderId`
2. 后端读接口
   - 先把列表和详情改为基于 `Listing`
3. 后端动作接口
   - 接单 / 预约 / 确认 / 完成全部切到 `Order`
4. 前端页面
   - 列表页加方向页签
   - 发布页改为方向驱动
   - 个人中心补齐四个视图
5. 定时任务
   - 自动过期
   - 自动切换 `BUSY / OPEN`
6. 兼容清理
   - 下线旧单向任务兼容逻辑

## 12. 最终建议

这次校园服务重构不应只是“多加一个分类”，而应明确完成两件事：

1. 从单向任务流改成双向供需市场
2. 从单条任务单接单人改成“发布内容 + 成交服务单”的两层模型

如果只在旧单向任务模型上继续叠字段，短期能跑，后续会在以下地方持续卡住：

- 多人预约
- 长期供给
- 数量上限
- 自动过期
- 会话拆分
- 个人中心多角色视图

因此，建议后续重构以本文档为准，优先完成 `Listing + Order + 自动过期 + 容量规则` 四件事。
