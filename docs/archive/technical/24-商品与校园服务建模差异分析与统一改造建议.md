# 商品与校园服务建模差异分析与统一改造建议

## 1. 文档目的

本文档用于回答四个问题：

1. 当前系统中的“商品”和“校园服务”到底是什么关系
2. 为什么它们在业务上相似，但在前后端实现上看起来像两套系统
3. 哪些部分适合统一，哪些部分不应该强行合并
4. 后续如果要逐步重构，应该按什么顺序改最稳

本文档不讨论理想化方案，而以当前代码真实状态为准，作为后续逐项修改的基线文档。

## 2. 结论摘要

当前“商品”和“校园服务”在业务本质上都属于“发布型对象”：

- 都有发布者
- 都有标题、描述、金额
- 都有状态、时间
- 都会出现在列表页、详情页、消息链路和个人中心中

但在当前实现里，它们已经演化成了两种不同的系统风格：

- 商品更像 `Listing + Commerce`
- 校园服务更像 `Listing + Workflow`

换句话说：

- 商品被实现为“资源实体 + 交易链路”
- 校园服务被实现为“任务实体 + 流程链路”

因此，当前问题不是“两个对象字段略有差异”，而是“缺少一层统一的上层抽象”，导致数据库、接口、前端类型和页面消费方式都不一致。

## 3. 当前状态分析

### 3.1 数据库层现状

商品模型定义在 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:128)：

- `Product`
- `ProductImage`
- `Favorite`
- `Order`

商品模型的核心特征：

- 主体字段是标题、描述、价格、分类、成色、标签、状态
- 通过 `sellerId` 绑定发布者
- 关联图片、收藏、订单、举报、行为记录

校园服务模型定义在 [backend/prisma/schema.prisma](/home/th1rt3en/dev/forge/SwapCampus/backend/prisma/schema.prisma:197)：

- `CampusServiceListing`
- `CampusServiceOrder`

校园服务模型的核心特征：

- 发布内容和成交单拆成两层
- `CampusServiceListing` 通过 `ownerId` 绑定发布者
- `CampusServiceOrder` 通过 `requesterId / providerId` 绑定协作双方
- 会话、状态流转、完成确认围绕 `CampusServiceOrder` 展开

当前数据库层可以得出两个判断：

1. 两者共享“发布内容”的上层语义
2. 两者底层并不是一个模型的不同类型，而是两张职责已经明显分化的领域表

### 3.2 后端接口层现状

商品控制器在 [backend/src/modules/products/products.controller.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/products/products.controller.ts:11)。

当前商品接口风格是标准资源风格：

- `GET /products`
- `GET /products/:id`
- `POST /products`

校园服务控制器在 [backend/src/modules/campus-services/campus-services.controller.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/campus-services/campus-services.controller.ts:15)。

当前校园服务接口已转为发布资源 + 服务单资源双层设计：

- `GET /campus-services`
- `GET /campus-services/:id`
- `POST /campus-services`
- `POST /campus-services/:id/orders`
- `GET /campus-service-orders`
- `POST /campus-service-orders/:id/confirm`
- `POST /campus-service-orders/:id/reject`
- `POST /campus-service-orders/:id/complete`
- `POST /campus-service-orders/:id/confirm-complete`
- `POST /campus-service-orders/:id/cancel`

这里最关键的差异有两个：

1. 商品有标准详情接口 `GET /products/:id`
2. 校园服务现在也已经补齐标准详情接口 `GET /campus-services/:id`

这说明校园服务当前已经从“先有流程动作，再围绕流程返回页面数据”逐步收口到资源化接口设计。

这说明：

- 商品后端是标准资源接口
- 校园服务后端也已经收口到资源化接口，只是领域上拆成了 `listing + order`

### 3.3 前端类型层现状

商品类型定义在 [frontend/src/services/api.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/api.ts:54)：

- `ProductSummary`
- `ProductDetail`

商品类型特点：

- 结构相对简洁
- 更像领域摘要数据
- 页面自己再拼装局部展示

校园服务类型定义在 [frontend/src/services/api.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/api.ts:318)：

- `CampusServiceListItem`
- `CampusServiceDetail`
- `CampusServiceOrderListItem`

校园服务类型仍然包含较多页面展示字段和动作字段，例如：

- `rewardLabel`
- `categoryLabel`
- `preview`
- `route`
- `schedule`
- `summaryTags`
- `timeline`
- `participantSummary`
- `viewerContext`
- `actionState`
- `actionLabels`

因此当前前端类型层存在明显分叉：

- 商品 DTO 更像“实体摘要”
- 校园服务 DTO 更像“页面 ViewModel”

但这里还需要补充一个更准确的判断：

- `ProductSummary` 确实偏轻量摘要
- `ProductDetail` 其实也已经是富视图对象
- 当前真正的问题是“商品侧列表轻、详情富；服务侧列表和详情共用一个过重 DTO”

这也是当前二者难以自然复用的重要原因。

### 3.4 后端装配层现状

商品后端会在 [backend/src/modules/products/products.service.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/products/products.service.ts:254) 中通过 `buildProductCards()` 组装卡片数据。

这层主要负责：

- 补卖家信息
- 补图片
- 补收藏数与收藏态
- 产出轻量摘要

校园服务后端则在 [backend/src/modules/campus-services/campus-services.service.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/campus-services/campus-services.service.ts:110) 直接把页面需要的大量结构一起组装出来，包括：

- 展示文案
- 时间线
- 标签
- 参与者摘要
- 用户视角权限
- 操作文案

这说明当前后端的输出层次也不一致：

- 商品返回的是偏“数据对象”
- 校园服务返回的是偏“视图对象”

### 3.5 页面层现状

商品搜索页和列表页围绕 `ProductSummaryCard` 消费商品摘要，见 [frontend/src/pages/SearchPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/SearchPage.tsx:186)。

校园服务列表页当前也在复用商品卡片壳，但方式是把服务任务转成 `ProductSummary` 再渲染，见 [frontend/src/pages/CampusServicesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/CampusServicesPage.tsx:46)。

这说明当前 UI 层已经开始靠拢，但方式仍然是“临时适配”，而不是统一的数据协议。

详情页层面，商品和服务都已经复用了 `DetailShell`：

- 商品详情见 [frontend/src/pages/ProductDetailPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/ProductDetailPage.tsx:335)
- 服务详情见 [frontend/src/pages/CampusServiceDetailPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/CampusServiceDetailPage.tsx:179)

这说明详情页骨架复用方向是对的，但数据结构和动作模型还没有统一。

### 3.6 搜索与筛选层现状

商品搜索参数定义在 [frontend/src/services/api.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/api.ts:120)，已有：

- `q`
- `category`
- `condition`
- `status`
- `trade`
- `sort`
- `minPrice`
- `maxPrice`
- `page`
- `pageSize`

校园服务查询参数定义在 [frontend/src/services/api.ts](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/services/api.ts:878)，当前只有：

- `category`
- `status`

而且校园服务页面里的更多筛选逻辑，目前主要是在前端本地数组上做，见 [frontend/src/pages/CampusServicesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/CampusServicesPage.tsx:217)。

因此，当前搜索与筛选能力并不是一套协议，也不在同一层完成。

### 3.7 列表返回形态现状

除了字段结构不同，商品和校园服务的“列表返回形态”也不一致。

商品列表接口返回的是分页结构：

- `items`
- `pagination`

校园服务列表接口当前已经返回分页容器：

- `page`
- `pageSize`
- `total`
- `totalPages`

这意味着当前问题不只是卡片字段不同，还包括：

- 列表容器协议不同
- 分页能力不同
- 页面消费方式不同

## 4. 当前问题归纳

综合来看，当前系统主要存在以下问题。

### 4.1 缺少统一的上层抽象

商品和校园服务都属于“发布内容”，但代码中没有明确的上层建模，例如：

- `ListingSummary`
- `ListingDetailBase`

于是页面在复用时只能靠临时字段转换。

### 4.2 DTO 风格不统一

当前商品接口偏领域实体，校园服务接口偏页面视图。

这会带来三个直接问题：

- 复用组件时要写很多适配代码
- 搜索和详情协议难以统一
- 页面层会越来越依赖后端的具体文案和按钮结构

更具体地说，旧校园服务总类型曾经同时承担了三类职责：

- 资源基础字段
- 页面展示字段
- 当前用户视角字段

其中像：

- `viewerContext`
- `actionState`
- `actionLabels`

本质上都属于 viewer-scoped 数据，不应长期和资源基础结构强耦合在一个总类型里。

### 4.3 校园服务详情链路不标准

缺少 `GET /campus-services/:id`，使得详情页读取方式不标准，也不利于后续复用商品详情页那套模式。

### 4.4 筛选与排序协议分裂

商品已经是“服务端查询 + 前端消费”模式。

校园服务目前仍有较多“先全量拉取，再在页面内筛选”的逻辑。

这会导致：

- 查询能力不一致
- 后续做统一筛选栏时难以抽象
- 数据量增大后性能和维护性都会变差

### 4.5 详情骨架虽已复用，但消费模型还不统一

`DetailShell` 的复用已经是一个好方向，但目前详情页的：

- 标题区
- 元信息区
- 行为按钮区
- 参与者区
- 时间线区

仍然没有基于统一数据层去消费。

### 4.6 列表响应协议尚未统一

当前商品列表已经形成：

- 分页查询参数
- 分页响应结构
- 页面按 `items + pagination` 消费

而校园服务列表仍然是：

- 轻量筛选参数
- 裸数组响应
- 页面端继续本地筛选和排序

如果这一层不先统一，后续即使抽出了 `ListingSummary`，页面仍然要在“容器协议”上继续分叉。

## 5. 哪些应该统一，哪些不该硬并

### 5.1 适合统一的部分

以下内容适合抽为统一上层：

- 列表摘要模型
- 列表响应容器
- 详情页基础骨架
- 发布者信息块
- 状态展示语义
- 搜索 / 筛选条协议
- 消息入口
- 通用卡片壳

### 5.2 不适合强行统一到底层的部分

以下内容不建议直接并成一套底层模型：

- 商品的图片、收藏、订单、举报、行为埋点
- 服务的接单、路线、履约、完成、取消流程

换句话说：

- 可以统一“展示层协议”
- 不要急着合并“领域实体”

## 6. 建议的目标结构

建议把目标结构分成三层理解。

### 6.1 领域层

领域层保留两个独立模型：

- `Product`
- `CampusServiceListing / CampusServiceOrder`

这层不要先动表，也不要为了统一而并表。

### 6.2 视图协议层

在接口层之上增加统一视图装配层。

建议至少定义两个上层协议：

#### 6.2.1 `ListingSummary`

建议包含：

- `id`
- `type`
- `title`
- `description`
- `amount`
- `amountLabel`
- `categoryKey`
- `categoryLabel`
- `status`
- `statusLabel`
- `publisher`
- `tags`
- `cover`
- `meta`

用途：

- 首页推荐流
- 搜索结果页
- 校园服务列表
- 用户主页的发布列表

建议注意一点：

- `ListingSummary` 只承接列表消费需要的稳定字段
- 不直接把按钮文案、权限、时间线等详情态字段塞进来

#### 6.2.2 `PaginatedListingResponse<T>`

建议包含：

- `items`
- `pagination.page`
- `pagination.pageSize`
- `pagination.total`
- `pagination.totalPages`

用途：

- 统一商品列表与校园服务列表的返回形态
- 为后续统一筛选栏和翻页交互提供稳定协议

#### 6.2.3 `ListingDetailBase`

建议包含：

- `id`
- `type`
- `title`
- `description`
- `amount`
- `amountLabel`
- `status`
- `statusLabel`
- `publisher`
- `timeline`
- `actions`
- `metaSections`

然后再做两种扩展：

- `ProductDetailView extends ListingDetailBase`
- `CampusServiceDetailView extends ListingDetailBase`

对于校园服务，建议保持当前已经开始采用的更清晰结构，例如：

- `CampusServiceListItemView`
- `CampusServiceDetailView`
- `CampusServiceViewerState`
- `CampusServiceActionState`

这样可以把“资源本身”和“当前用户看见什么、能做什么”拆开。

### 6.3 页面消费层

页面层只消费统一的摘要和详情基类，再通过类型特定字段补差异化区域。

这样可以做到：

- 卡片组件可复用
- 筛选栏可复用
- 详情骨架可复用
- 页面只在真正差异处做分支

## 7. 分步改造建议

以下顺序是当前最稳妥的修改路径。

### 7.1 第一步：补齐校园服务标准详情接口

建议新增：

- `GET /campus-services/:id`

目标：

- 让服务详情页不再依赖“先拉列表再筛一条”
- 对齐商品详情页的资源读取方式
- 为详情页基类统一做准备

### 7.2 第二步：补齐校园服务列表查询协议

在补完标准详情接口后，下一步更应该先收敛列表查询协议，而不是立刻抽详情基类。

建议优先补齐：

- 分页参数
- 排序参数
- 最低 / 最高酬谢
- 信用筛选
- 关键词查询

目标：

- 让校园服务列表从“先拉全量、前端本地筛选”转为“服务端查询 + 前端消费”
- 先统一最影响复用和性能的列表层
- 为统一 `ListingSummary` 和列表响应容器做准备

### 7.3 第三步：拆分校园服务 DTO

把旧校园服务大总类型中混在一起的内容拆成两层：

1. 领域字段
2. 视图装配字段

进一步说，至少不要继续让单个类型同时承担：

- 数据实体
- 页面文案
- 行为权限
- 按钮标签

更稳妥的拆法是：

1. 列表项视图
2. 详情视图
3. viewer / actions 覆盖层

### 7.4 第四步：定义统一摘要协议

新增统一类型，例如：

- `ListingSummary`

然后：

- 商品列表返回或映射到该协议
- 校园服务列表返回或映射到该协议

同时补一个统一列表响应容器，例如：

- `PaginatedListingResponse<ListingSummary>`

这一步完成后，搜索结果页和校园服务列表页的卡片消费方式才能真正统一。

### 7.5 第五步：定义统一详情基类

新增统一类型，例如：

- `ListingDetailBase`

让 `ProductDetailPage` 和 `CampusServiceDetailPage` 先共享数据消费结构，再保留各自领域差异块。

### 7.6 第六步：统一筛选栏查询协议

把“商品搜索”和“校园服务筛选”提升为同一套可复用机制。

建议先统一这些高频筛选项：

- 综合排序
- 价格排序
- 区间筛选
- 信用筛选
- 类型筛选
- 状态筛选

这里的“统一”不是所有业务都用完全相同字段，而是统一成同一个筛选组件协议和服务端查询约定。

### 7.7 第七步：统一个人中心中的“我发布的内容”视图

当上层摘要协议稳定后，可以进一步把个人中心中的：

- 我卖出的商品
- 我发布的服务
- 我接下的服务

整理成更统一的内容视图。

## 8. 推荐的修改优先级

如果你准备逐个改，建议按下面优先级推进。

### 优先级 A：先改接口与类型

1. 补 `GET /campus-services/:id`
2. 补齐校园服务列表查询 / 分页协议
3. 拆校园服务 DTO
4. 定义统一 `ListingSummary`
5. 定义统一列表响应容器

原因：

- 这是最底层的结构统一
- 不先做这一步，页面复用会一直靠适配层撑着
- 当前最重的适配压力实际发生在列表层，而不只是详情层

### 优先级 B：再改详情页与筛选栏

1. 统一详情基类
2. 统一筛选协议
3. 把服务列表从本地筛选逐步改成服务端查询

原因：

- 这一步直接改善页面复用和查询体验

### 优先级 C：最后再整理个人中心与推荐链路

1. 统一“发布型内容”列表展示
2. 统一消息入口
3. 再看是否需要引入跨类型推荐或统一发布流

原因：

- 这些属于建立在前面结构稳定后的收益项

## 9. 不建议现在做的事情

为了避免重构失控，当前阶段不建议做以下动作：

### 9.1 不建议直接并表

当前 `Product` 和 `CampusServiceListing / CampusServiceOrder` 的领域差异已经很明显，直接并表会把模型搞得更重、更难维护。

### 9.2 不建议先统一数据库，再倒推页面

当前真正的问题主要在接口协议和前端消费层，不在库表本身。

### 9.3 不建议重新引入笼统的校园服务大总类型

应该继续保持列表、详情、订单、viewer/action 状态分层，不要再把它们塞回一个总类型。

## 10. 一句话总结

当前商品和校园服务不是“两个差不多的对象”，而是：

- 底层是两个独立领域模型
- 上层本应共享同一个“发布型对象”抽象
- 但这层抽象现在还没有被明确建立出来

后续最合理的改法不是强行合并底层，而是：
