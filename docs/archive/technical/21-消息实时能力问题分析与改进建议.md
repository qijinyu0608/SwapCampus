# 消息实时能力问题分析与改进建议

## 1. 当前状态判断

当前消息模块已经能完成“会话列表、消息查询、发送消息、Socket.IO 实时追加”的主链路，足够课程演示，但仍明显偏“演示级 IM”，还没有完整的消息系统能力。

关键证据：

- WebSocket 已实现握手认证、房间订阅权限校验和新消息广播，见 [backend/src/modules/messages/messages.gateway.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/messages/messages.gateway.ts:1)
- 消息 REST 接口当前已统一挂载认证守卫，并从服务端会话解析当前用户，见 [backend/src/modules/messages/messages.controller.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/messages/messages.controller.ts:1)
- 前端未读态用 `localStorage` 记录，见 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:109)
- 前端通过 `socket.emit('message:join')` 订阅房间，通过 `message:new` 接收新增消息，见 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:321) 和 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:468)
- README 已明确说明消息是“演示级实时推送”，见 [README.md](/home/th1rt3en/dev/forge/SwapCampus/README.md:39)

## 2. 当前问题拆解

### 2.1 Socket 层已经补上身份校验，但仍未形成完整 IM 能力

`MessagesGateway` 现在会在握手阶段校验 `SuperTokens access token`，并在 `message:join` 前校验当前用户是否属于该会话，见 [backend/src/modules/messages/messages.gateway.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/messages/messages.gateway.ts:1)。

这意味着：

- 非会话参与者不能再直接加入消息房间
- 连接身份已经和登录态发生了服务端绑定
- 但在线状态、已读回执、断线补偿仍未落地

### 2.2 消息权限已从客户端传参切回服务端会话

当前消息查询、发起会话、发送消息等主链路均从服务端认证态推导当前用户，不再依赖 `userId` / `senderId` 作为操作者身份来源。

这会导致：

- 权限边界已经比旧版本稳定很多
- 但演示补水、未读状态、多端一致性仍未全部收口

### 2.3 已读/未读状态只保存在前端

`MessagesPage` 使用 `READ_STORAGE_PREFIX` 把已读时间写入本地存储，见 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:27) 与 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:327)。

这意味着：

- 未读数不是数据库事实
- 换设备就全部“未读重置”
- 无法在后台或多端展示统一未读状态

### 2.4 缺少消息投递确认、断线补偿和重放

当前 `applyRealtimeMessage()` 主要是收到 `message:new` 后更新当前 UI，见 [frontend/src/pages/MessagesPage.tsx](/home/th1rt3en/dev/forge/SwapCampus/frontend/src/pages/MessagesPage.tsx:277)。

但系统还缺少：

- 服务端 ACK
- 断线重连后的消息补拉策略
- 最后游标或最后已收消息 ID
- 失败发送重试

这也是 README 自己点出的短板，见 [README.md](/home/th1rt3en/dev/forge/SwapCampus/README.md:39)。

### 2.5 Demo hydrate 逻辑仍说明消息样本依赖“演示补水”

`/messages/demo-hydrate` 当前已改为“登录后、开发态、只对当前会话用户补水”的内部演示接口，但它仍然属于演示辅助能力。

这很适合课程展示，但也说明：

- 当前消息模块在“初始活跃度”和“演示丰满度”上依赖脚本补足
- 不是一个完全按真实用户流自然长出来的消息域

## 3. 影响评估

### 3.1 对课程演示的影响

这套已经足够展示“聊得起来、订单能联动、消息能刷新”。

### 3.2 对真实产品化的影响

如果进入真实多人使用场景，当前实现会在这些地方先暴露问题：

- 权限边界
- 多端一致性
- 未读统计
- 重连和消息丢失
- 在线状态和回执能力

## 4. 改进建议

### 4.1 第一阶段：补身份和会话授权

建议优先完成：

1. 保持 HTTP 与 Socket 统一使用认证态
2. 继续限制或移除演示补水接口
3. 把未读状态从本地迁到服务端
4. 拒绝非法房间订阅

### 4.2 第二阶段：把已读状态落库

建议新增会话参与者表或会话读指针表，例如：

- `ConversationParticipant`
- `ConversationReadCursor`

核心字段建议包含：

- `conversationId`
- `userId`
- `lastReadMessageId`
- `lastReadAt`

### 4.3 第三阶段：补消息可靠性

建议至少补这些能力：

- `sendMessage` 返回服务端确认 ID
- 前端维护 optimistic message -> confirmed message 映射
- 断线后根据最后消息时间或 ID 补拉
- 每次打开会话时执行一次增量同步

### 4.4 第四阶段：把实时推送从“广播新消息”升级为“消息域事件”

当前网关只广播 `message:new`，见 [backend/src/modules/messages/messages.gateway.ts](/home/th1rt3en/dev/forge/SwapCampus/backend/src/modules/messages/messages.gateway.ts:44)。

建议后续扩展事件：

- `message:new`
- `message:read`
- `conversation:updated`
- `presence:online`
- `presence:offline`

## 5. 推荐实施顺序

1. 已读状态落库
2. 增量补拉与 ACK
3. 在线状态与回执
4. 进一步移除演示补水依赖
