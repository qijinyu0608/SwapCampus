# 消息、推荐、治理与异步化改造说明

## 1. 目的

本文档说明如果要把当前系统里的 `消息`、`推荐`、`治理`、`搜索/电商同步` 这几块进一步改成 MQ 驱动或微服务拆分，应该改哪些文件、先改什么、后改什么。

## 2. 现状

- `search-indexer`、`commerce-sync` 和 `governance-worker` 已经是独立异步进程
- 主后端仍是单体 NestJS，消息和推荐还在 backend 内消费 Outbox
- 搜索、电商同步仍主要基于 MySQL Outbox 轮询
- 治理审计已经升级为 `Outbox + RabbitMQ + governance-worker`

## 3. 优先级

建议按下面顺序改：

1. 消息通知
2. 推荐与行为分析
3. 举报/审核/封禁治理和审计 worker 收口
4. Outbox 从轮询升级到真正 MQ
5. 再评估独立微服务拆分

## 4. 各部分怎么改

### 4.1 消息

当前落点：

- `backend/src/modules/messages/messages.service.ts`
- `backend/src/modules/messages/messages.gateway.ts`
- `frontend/src/pages/MessagesPage.tsx`

建议改法：

- `sendMessage` 落库后不直接只靠 `emitNewMessage`
- 改为先发 `message.sent` 领域事件
- 由独立消息服务或消息 worker 处理：
  - 房间广播
  - 未读数
  - 在线状态
  - 推送通知

推荐再补：

- `ConversationReadCursor`
- `ConversationParticipant`
- `MessageDeliveryLog`

### 4.2 推荐

当前落点：

- `backend/src/modules/products/products.service.ts`
- `backend/src/modules/products/products.controller.ts`
- `backend/src/modules/users/users.service.ts`

建议改法：

- 把 `UserBehavior`、收藏、联系、下单、浏览统一写成行为事件
- 新增 `behavior.tracked` / `favorite.changed` / `order.completed` 这类事件
- 独立推荐服务消费这些事件，负责：
  - 行为聚合
  - 召回
  - 排序
  - 首页推荐

推荐再补：

- `RecommendationProfile`
- `RecommendationFeatureSnapshot`
- `RecommendationJob`

### 4.3 治理

当前落点：

- `backend/src/modules/reports/reports.service.ts`
- `backend/src/modules/admin/admin.service.ts`
- `backend/src/modules/users/users.service.ts`
- `backend/src/governance-worker.main.ts`
- `backend/src/governance-worker.module.ts`
- `backend/src/governance-worker.module.spec.ts`
- `governance-worker/Dockerfile`

建议改法：

- 举报、封禁、解封、下架、订单取消这些动作改成治理事件
- 主后端通过 Outbox 把治理事件发布到 RabbitMQ
- 由独立 `governance-worker` 统一消费 RabbitMQ 审计事件
- 主后端只保留最小事务写入和事件发布，后续再决定是否继续拆治理编排服务

推荐拆分职责：

- 主后端：写库、校验、写 Outbox、发布 MQ
- 治理服务：审核编排、审计日志、补偿、通知

### 4.4 搜索 / 电商同步

当前落点：

- `backend/src/modules/outbox/*`
- `backend/src/search-indexer.main.ts`
- `backend/src/commerce-sync.main.ts`
- `docker-compose.yml`

建议改法：

- 保留 Outbox 作为事务边界
- 把 Outbox 消费者替换成 MQ 消费者
- 事件 topic 仍然保留，作为跨服务契约

## 5. 推荐的实施顺序

### 第一步

先把消息改成事件驱动，但仍保留单体内消费。

### 第二步

把推荐行为单独抽成 consumer，不先拆服务。

### 第三步

把治理事件收口到独立审计服务，并切到 RabbitMQ。

### 第四步

再把 Outbox 替换为 RabbitMQ / Kafka / Redis Stream 之一。

### 第五步

最后再决定是否把 `messages`、`recommendations`、`admin-audit` 真拆成独立服务。

## 7. 落地原则

- 主业务先保持可用
- 先事件化，再拆服务
- 先解耦副作用，再拆核心交易
- 不要一开始就把 `products`、`orders` 这种强事务域拆出去

## 8. 结论

这几个部分最合理的改法是：

`消息`、`推荐` 先事件化，`治理` 已经落地 `Outbox + RabbitMQ + 审计 worker`，`搜索/电商同步` 继续作为异步基础设施，然后再决定要不要把其他部分继续升级到 MQ 和更完整的独立微服务。
