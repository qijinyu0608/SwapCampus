# 文档管理与版本规范

## 1. 目的
本规范用于建立一套完整、规范、可追溯的软件工程文档体系，确保需求、设计、实现、测试、验收与部署文档长期保持一致。

## 2. 管理原则
- 文档与代码同仓维护，文档属于一等交付物，不允许开发结束后集中补写。
- 现行主文档统一放在 `docs/` 根目录；历史过程材料允许归档到 `docs/archive/`。
- 统一采用 Markdown，现行主文档命名使用编号加中文标题的方式。
- 每份文档都必须能回答三个问题：对应什么需求、基于什么实现、由什么证据验证。
- 对运行中可能变化的数据，统一区分“可复现种子基线”和“当前运行快照”两种口径，避免把动态数据误写成固定常量。

## 4. 统一编写标准
- 使用简体中文叙述，代码、接口、路径、命令保持原始语言。
- 对系统事实的描述优先引用当前代码、接口返回、SQL 查询结果或构建/测试输出。
- 涉及数量、账号、端口、模块名时，必须与当前实现一致。
- 需求类文档写“应当做什么”，设计类文档写“如何实现”，测试与验收文档写“如何证明已经做到”。
- 历史过程类文档允许保留阶段性决策，但必须标注“当时口径”或“后续演进结果”，避免和现状混淆。

## 5. 版本管理机制
- 当前项目采用“代码与文档同仓同版本”的管理方式，文档文件与源码一起纳入仓库工作区。
- 关键里程碑变更需要同时更新三类记录：
  - 计划与过程：`10-项目计划.md`、`13-开发记录.md`
  - 证明与验收：`06-测试计划与测试报告.md`、`14-验收与演示记录.md`
  - 交付与追溯：`16-交付清单.md`、`17-任务需求实现追踪矩阵.md`
- 若变更涉及数据规模、初始化口径、部署方式、页面结构、模块边界或权限规则，必须在同一轮内完成文档同步。

## 6. 更新触发规则
出现以下情况时，必须同步更新文档：
- 新增或删除模块
- 调整数据库结构或种子规模
- 修改初始化口径、权限规则、审核流程或部署方式
- 页面信息架构发生明显变化
- 新增测试项、验收项或运行截图
- 对课程设计交付口径作出变更

## 7. 一致性校对清单
每轮交付前至少核对以下内容：
- `02-需求规格说明书.md` 的功能要求是否都能在 `17-任务需求实现追踪矩阵.md` 中找到实现与证据
- `03-概要设计说明书.md` 与 `04-详细设计说明书.md` 的模块划分是否仍与代码目录一致
- `05-数据库设计说明书.md` 中的数据模型、种子基线和表名是否与 Prisma schema 一致
- `06-测试计划与测试报告.md`、`14-验收与演示记录.md` 中的统计值、接口和页面行为是否与当前系统一致
- `08-部署与运维手册.md`、`16-交付清单.md` 中的启动方式、端口与初始化口径是否一致
- `docs/archive/` 中的历史材料是否仍被主入口误标为现行基线

## 8. 当前执行口径
截至 `2026-06-15`，本项目文档执行以下口径：
- 默认初始化口径：用于说明 `make init` 后空库建表的默认状态
- 可选演示种子口径：用于说明手动执行 `db:reset-and-seed-demo` 后可重建的演示数据规模
- 追溯关系：统一以 `17-任务需求实现追踪矩阵.md` 作为需求、实现与证据的总索引
