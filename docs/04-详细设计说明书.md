# 详细设计说明书

## 1. 用户与认证模块
- 输入：学号、姓名、邮箱、密码
- 输出：登录 token、用户基础信息、认证状态
- 关键接口：`POST /api/auth/register`、`POST /api/auth/login`

### 1.1 注册流程
1. 前端提交学号、姓名、邮箱、密码
2. 后端创建 `users` 记录
3. 同时创建 `student_verifications` 记录，状态默认为 `PENDING`
4. 返回用户基础信息，供前端本地缓存当前登录用户

### 1.2 登录流程
1. 前端提交学号或邮箱与密码
2. 后端按学号/邮箱查询用户
3. 返回登录 token 与用户基本信息
4. 前端在浏览器本地保存当前登录用户

### 1.3 当前边界
当前版本主要用于课程设计交付，已完成密码校验，但尚未加入完整 JWT 守卫。

## 2. 商品模块
- 商品实体包含标题、分类、价格、成色、标签、图片列表、状态
- 后续接口：创建商品、更新商品、查询商品列表、查询商品详情

### 2.1 当前已实现接口
- `GET /api/products`：读取首页商品流
- `GET /api/products/recommendations?userId=:id`：读取个性化推荐流
- `GET /api/products/publishing-rules`：读取发布规则、禁售词和白名单提示
- `GET /api/products/dashboard`：读取统计数据
- `GET /api/products/:id`：读取商品详情、卖家画像、统计信号与同类推荐
- `POST /api/products`：创建新商品

### 2.2 商品创建流程
1. 前端页面获取当前登录用户 ID 作为 `sellerId`
2. 用户填写标题、分类、价格、成色、标签和描述
3. 后端写入 `products` 表，状态默认为 `PENDING`
4. 新商品写入成功后，首页商品流顶部可见

### 2.3 数据展示策略
- 商品价格从数据库 Decimal 字段转换为前端 number
- 标签字段按逗号拆分为数组，便于页面展示
- 发布者名称在当前版本优先展示真实昵称，不足时使用账号编号兜底

### 2.4 错误处理策略
- 当数据库链路不可用时，保留 fallback 数据用于前端兜底展示
- 当前容器环境已完成 Prisma 兼容修复，默认应走真实数据库数据
- 当登录态失效、账号被封禁或发布内容命中禁售规则时，接口返回明确错误消息供前端提示

### 2.5 可维护性设计
- 前端通过 `services/api.ts` 集中封装商品接口
- 服务层统一完成状态字段映射和数据转换，避免页面散落业务规则
- 商品状态使用枚举管理，便于后续扩展售罄、锁定等状态
- 商品图、地点文案、描述模板与推荐逻辑尽量集中封装，避免页面硬编码业务信息
- 商品发布规则集中由后端维护，前端只做展示与提交，不复制审核规则

## 3. 订单模块
- 订单关联下单账号、发布账号和商品
- 状态流转：待约定 -> 待面交 -> 待评价 -> 已完成；在未完成前可取消
- 订单只承接校内线下面交，不设计线上付款、发货、物流、收货流程

### 3.1 当前已实现接口
- `POST /api/orders`：创建订单
- `GET /api/orders`：查询最新订单列表
- `PATCH /api/orders/:id/meetup`：确认或修改线下面交时间地点
- `PATCH /api/orders/:id/cancel`：取消订单
- `PATCH /api/orders/:id/complete`：确认线下面交完成
- `POST /api/orders/:id/reviews`：提交交易评价

### 3.2 创建订单流程
1. 前端提交商品 ID、下单账号 ID、面交地点与备注
2. 后端根据商品 ID 查询商品信息
3. 自动从商品中提取发布账号 ID
4. 创建订单，状态初始化为 `PENDING`
5. 商品状态临时调整为 `OFFLINE`，避免在交易协商期继续被重复下单
6. 系统同步建立关联会话并写入第一条订单沟通消息
7. 下单用户跳转到个人中心的“我买到的”订单列表

### 3.3 当前状态设计
- `PENDING`：已下单，待双方约定线下面交时间地点
- `IN_PROGRESS`：已约定，待线下面交
- `WAITING_REVIEW`：线下面交已完成，待评价
- `COMPLETED`：评价完成，交易完成，商品标记为已售
- `CANCELED`：订单取消；若没有其他活跃或已完成订单，商品恢复在售

### 3.4 线下面交操作流程
1. 买家下单后，系统自动建立订单会话。
2. 买卖双方通过消息沟通约定时间地点。
3. 任一订单参与方可确认或修改面交安排，订单进入 `IN_PROGRESS`。
4. 任一订单参与方可在成交前取消订单。
5. 面交完成后，参与方确认完成，订单进入 `WAITING_REVIEW`。
6. 用户提交评分和评价内容后，订单进入 `COMPLETED`。

## 4. 消息模块
- 会话按订单或商品上下文建立
- 消息类型包括文本、图片、表情
- 当前版本使用 HTTP 写库 + Socket.IO 房间广播模式，支持消息页实时追加新消息

### 4.1 当前实现状态
数据库层已经包含 `conversations` 与 `messages` 表，种子数据中已写入样例会话。
当前已实现：
- `GET /api/messages/conversations`
- `GET /api/messages/conversations/:id`
- `POST /api/messages/conversations/:id`
- Socket.IO `message:join` 加入会话房间
- Socket.IO `message:new` 推送已落库的新消息

前端消息页已接入真实会话摘要、消息明细读取、消息发送与实时推送，用于演示交易上下文中的沟通记录。

### 4.2 消息发送流程
1. 前端读取浏览器本地保存的当前登录用户信息
2. 用户在会话窗口输入消息内容
3. 前端调用 `POST /api/messages/conversations/:id`
4. 后端写入 `messages` 表并更新 `conversations.updatedAt`
5. 后端通过 Socket.IO 向 `conversation:{id}` 房间广播 `message:new`
6. 前端收到推送后追加消息并更新左侧会话预览

### 4.3 后续增强思路
- 用户进入商品页或订单页后创建会话
- 消息落库，保证答辩时可回放对话历史
- 继续补充已读回执、在线状态、断线补偿和更严格的用户鉴权
- 当并发提高时，可通过消息队列把通知、未读数统计、风控记录拆为异步任务

## 5. 校园服务模块
- 校园服务任务与普通商品流分离，使用独立数据模型和独立页面承载
- 当前任务类型包括 `ERRAND`、`AGENCY`、`GROUP_BUY`、`HELP`

### 5.1 当前已实现接口
- `GET /api/campus-services`
- `POST /api/campus-services`
- `POST /api/campus-services/:id/accept`
- `POST /api/campus-services/:id/complete`

### 5.2 任务发布流程
1. 普通用户在校园服务页填写标题、类别、起点、终点、奖励、截止时间和说明
2. 后端创建 `CampusServiceTask`
3. 状态初始化为 `OPEN`
4. 页面右侧委托列表立即可见

### 5.3 接单与完结流程
1. 其他普通用户选择开放任务并接单
2. 后端更新 `accepterId` 与任务状态为 `MATCHED`
3. 系统自动建立关联会话，方便双方继续沟通
4. 发布者或接单人可在任务完成后标记为 `DONE`

## 6. 想要、偏好与推荐行为模块
- 想要列表当前采用浏览器本地存储按用户作用域隔离
- 最近浏览和想要数据会在前端形成轻量偏好画像
- 当当前用户为普通用户时，`VIEW`、`FAVORITE`、`UNFAVORITE`、`CONTACT`、`ORDER` 会同步上报后端

### 6.1 当前实现状态
- 首页根据本地画像和后端推荐结果共同决定展示顺序
- 想要页按收藏顺序展示商品，并支持直接取消想要
- 浏览商品详情会触发最近浏览记录和后端去重写入

### 6.2 设计考虑
- 当前版本优先保证“想要”和推荐信号可用，不额外引入独立收藏后端模型
- 用户未登录或以游客身份浏览时，仅保留本地偏好，不写入后端行为表
- 后续若需要多端同步，可将本地收藏迁移到 `Favorite` 表并复用现有行为事件

## 7. 推荐与行为模块
- 推荐结果基于用户历史行为与商品热度生成
- 行为事件包括 `VIEW`、`FAVORITE`、`UNFAVORITE`、`CONTACT`、`ORDER`

### 7.1 当前实现状态
- 首页默认调用推荐接口或商品列表接口
- 后端使用分类偏好、标签偏好、收藏商品、浏览记录与热度进行排序
- 行为数据写入 `UserBehavior`，为后续更复杂推荐算法保留扩展位

### 7.2 设计考虑
- 当前算法优先保证可解释和稳定，而不是追求复杂模型
- 排序逻辑收敛在服务层，避免前端自行拼装推荐规则
- 后续可继续引入召回、重排、冷启动和批处理推荐任务

## 8. 用户资料与信用模块
- 提供 `GET /api/users/:id/profile`、`PATCH /api/users/:id/profile`、`GET /api/users/:id/trust-summary`
- 个人中心同时展示基础资料、信用摘要、线下面交订单分页和已发布商品
- 个人资料支持独立详情页，便于从侧栏“个人资料”入口单独查看账号、实名和信用信息

### 8.1 资料维护流程
1. 前端读取当前登录用户资料与实名信息
2. 用户在个人中心编辑姓名、邮箱、真实姓名、学院和手机号
3. 后端更新 `User` 与 `StudentVerification`，若实名记录不存在则执行 `upsert`
4. 前端同步刷新本地登录用户信息和信用摘要

### 8.2 信用摘要计算
- 信用等级根据 `creditScore` 转换为 `优秀 / 稳定 / 正常 / 待提升`
- 回复率根据实名状态和发送消息数估算
- 成交数、进行中订单数、待评价订单数来源于订单聚合
- 平均评分当前来源于 `Review` 表，若暂无记录则回退演示默认值

## 9. 管理模块
- 审核商品合法性
- 受理举报
- 维护用户封禁状态

### 9.1 当前实现状态
当前后台页重点展示治理视角，包括：
- 待审核商品数量
- 举报队列结构
- 管理员处理对象、处理原因、状态标签

当前已实现：
- `GET /api/admin/overview`
- `PATCH /api/admin/products/:id/status`
- `PATCH /api/reports/:id/resolve`
- `GET /api/users/moderation/list`
- `PATCH /api/users/:id/ban`
- `PATCH /api/users/:id/unban`

其中：
- `GET /api/admin/overview` 返回待审核商品数、用户总数、举报数和最近待审核商品列表
- `PATCH /api/admin/products/:id/status` 支持将商品从 `PENDING` 更新为 `ON_SALE` 或 `OFFLINE`
- `PATCH /api/reports/:id/resolve` 支持举报处理结果与 `BAN_USER / UNBAN_USER` 联动
- 用户治理接口支持读取用户状态并手动执行封禁与解除封禁

前端后台页已接入上述接口，管理员可直接执行审核通过、下架、举报处理、封禁与解除封禁。

### 9.2 后续扩展方向
- 举报分级、处罚时长与申诉处理
- 更细粒度的用户治理台账
