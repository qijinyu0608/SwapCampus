# AI 部署启动与测试指南

## 1. 目的

本文档给后续 AI 或开发人员提供一套可直接执行的本地部署、启动、测试和排障步骤。

目标不是解释概念，而是保证接手的人按本文档即可把项目跑起来，并知道哪些忽略文件需要单独分发。

## 2. 先看结论

当前项目的容器链路已经按 2026-06-15 实测通过：

- `backend`：可构建、可启动、`/api/health` 返回正常
- `frontend`：可构建、可启动、首页可访问
- `vendure`：可构建、可启动、`/health` 与 `/dashboard/` 可访问
- `db-init`：执行后应为 `Exited (0)`
- `mysql`、`minio`、`meilisearch`、`supertokens-db`、`supertokens`：可正常联动

## 3. AI 执行固定顺序

后续任何 AI 接手部署时，固定按下面顺序执行，不要跳步骤：

1. 在仓库根目录确认是否已有 `.env`
2. 若没有 `.env`，先参考根目录 `.env.example` 新建
3. 先执行 `make init`
4. 再执行 `make start`
5. 执行 `docker compose ps -a`
6. 执行 `curl http://127.0.0.1:3001/api/health`
7. 执行 `curl http://127.0.0.1:3001/api/products/publishing-rules`
8. 执行 `curl http://127.0.0.1:3001/api/products/dashboard`
9. 执行 `curl -I http://127.0.0.1:5178`
10. 若要检查 Vendure，再执行 `curl http://127.0.0.1:3002/health`

不要把 `make init` 和“清库重置”混为一谈。当前默认 `make init` 不会强制清空业务数据。

## 4. 启动命令

### 4.1 默认初始化

```bash
make init
make start
```

说明：

- `make init` 只做 `prisma db push` 和空库初始化检查
- `make start` 会启动 `mysql`、`minio`、`meilisearch`、`supertokens-db`、`supertokens`、`vendure`、`backend`、`frontend`

### 4.2 强制重置数据库

仅在明确需要清空并重建数据库时执行：

```bash
make init-reset
make start
```

### 4.3 完整清空容器和数据

```bash
docker compose down -v
make init
make start
```

## 5. API 如何单独配置

这里必须区分两类配置，不要混写。

### 5.1 后端运行时 API 配置

这些值由 `docker-compose.yml` 在容器启动时注入，主要影响：

- 后端生成的公开链接
- SuperTokens 的 `apiDomain` / `websiteDomain`
- 媒体文件公开地址
- 后端访问 Vendure、SuperTokens、DeepSeek 的行为

根目录 `.env` 可覆盖这些值：

```env
API_DOMAIN=http://127.0.0.1:3001
WEBSITE_DOMAIN=http://127.0.0.1:5178
SUPERTOKENS_API_KEY=
VENDURE_ADMIN_TOKEN=
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
ENABLE_DEV_AUTH_FALLBACK=true
```

如果后端对外地址变化，至少要同步改：

- `API_DOMAIN`
- `WEBSITE_DOMAIN`

### 5.2 前端构建时 API 配置

前端不是运行时动态读取，而是在构建镜像时通过 `VITE_*` 写入。

根目录 `.env` 可覆盖这些值：

```env
VITE_API_BASE_URL=http://127.0.0.1:3001/api
VITE_API_DOMAIN=http://127.0.0.1:3001
VITE_SOCKET_URL=http://127.0.0.1:3001
VITE_WEBSITE_DOMAIN=http://127.0.0.1:5178
```

修改这些值后，必须重新构建前端镜像：

```bash
docker compose build frontend
docker compose up -d frontend
```

### 5.3 当前实现上的优先级

当前前端逻辑已调整为：

1. 优先使用 `VITE_API_BASE_URL` / `VITE_API_DOMAIN` / `VITE_WEBSITE_DOMAIN`
2. 未配置时，才根据浏览器地址推导本地默认值

所以如果后续要把 API 地址单独分发给开发人员，必须把根目录 `.env` 一起发过去，而不是只口头说明。

## 6. 哪些 ignore 文件要单独分发

后续给开发人员或 AI 分发项目时，下面这些文件或目录可能不在 Git 里，但又很重要：

### 6.1 必须单独分发的配置文件

- 根目录 `.env`
- `backend/.env`
- `vendure/.env`

说明：

- `backend/.env` 主要用于本机非 Docker 启动或脚本执行
- `vendure/.env` 主要保存本地 Vendure 默认配置
- 根目录 `.env` 是 Docker Compose 覆盖入口，后续部署最关键

### 6.2 不建议分发的数据目录

以下目录通常不应该直接交给后续开发人员作为“源码配置”的一部分：

- `mysql-data/`
- `minio-data/`
- `meilisearch-data/`
- `supertokens-pg-data/`
- `vendure-data/`

这些是运行时数据，不是配置模板。

### 6.3 需要视场景决定的文件

- `vendure-data/vendure.sqlite`

说明：

- 如果要保留当前 Vendure 状态，可一并分发
- 如果只需要一套可重建环境，不必分发，容器会重新生成

## 9. 常见故障与处理

### 9.1 `db-init` 报 Prisma / OpenSSL 错误

先确认使用的是当前仓库中的最新 `backend/Dockerfile`。该问题已通过在镜像基础层安装 `openssl` 修复。

### 9.2 `db-init` 报 `tsx: not found`

说明初始化容器错误地使用了裁剪掉 dev 依赖的镜像。当前仓库已经修复为：

- `builder` 保留 dev 依赖，供 `db-init` 使用
- `runner` 使用裁剪后的依赖，供 `backend` 正式运行

### 9.3 `vendure` 构建失败，提示 `better-sqlite3` 编译问题

说明缺少 `python3`、`make`、`g++`。当前仓库中的 `vendure/Dockerfile` 已安装这些构建依赖。

### 9.4 `frontend` 容器名冲突

若出现类似：

```text
Conflict. The container name "/swapcampus-frontend-1" is already in use
```

执行：

```bash
docker rm -f swapcampus-frontend-1
make start
```

### 9.5 改了根目录 `.env` 但前端地址没变

这是因为前端配置属于构建时变量，必须重新构建：

```bash
docker compose build frontend
docker compose up -d frontend
```
