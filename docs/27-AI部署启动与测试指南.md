# AI 部署启动与测试指南

## 1. 目的

本文档面向后续接手项目的开发人员或自动化代理，目的是提供一套可以直接执行的本地部署、启动、测试和排障步骤。它不强调概念介绍，而强调“按当前仓库实际情况，怎样最快把系统跑起来，并知道哪些文件需要单独准备”。

## 2. 先看结论

按 `2026-06-15` 的实测结果，当前项目的容器链路已经可以正常运行：`backend` 可构建并正常返回 `/api/health`；`frontend` 可构建并正常访问首页；`vendure` 可构建并访问 `/health` 与 `/dashboard/`；`db-init` 执行完成后应显示为 `Exited (0)`；`mysql`、`minio`、`meilisearch`、`supertokens-db` 与 `supertokens` 均可正常联动。

## 3. AI 执行固定顺序

后续任何自动化代理或新接手人员在部署时，都建议严格按下面顺序执行，不要跳步：

1. 在仓库根目录确认是否已有 `.env`
2. 若没有 `.env`，先参考根目录 `.env.example` 新建
3. 先执行 `make init`
4. 再执行 `make start`
5. 执行 `docker compose ps -a`
6. 执行 `curl http://127.0.0.1:3001/api/health`
7. 执行 `curl http://127.0.0.1:3001/api/products/publishing-rules`
8. 执行 `curl http://127.0.0.1:3001/api/products/dashboard`
9. 执行 `curl -I http://127.0.0.1:5178`
10. 若要检查 Vendure，再执行 `curl http://127.0.0.1:3002/health`

这里需要特别说明：`make init` 与“清库重置”不是同一件事。当前默认 `make init` 不会强制清空业务数据，只负责建表和初始化检查。

## 4. 启动命令

### 4.1 默认初始化

```bash
make init
make start
```

默认初始化的含义，是在当前数据库状态基础上完成 `prisma db push` 与空库检查；`make start` 则会拉起 `mysql`、`minio`、`meilisearch`、`supertokens-db`、`supertokens`、`vendure`、`backend` 和 `frontend`。

### 4.2 强制重置数据库

只有在明确需要清空并重建数据库时，才执行下面这组命令：

```bash
make init-reset
make start
```

### 4.3 完整清空容器和数据
当容器状态或挂载数据已经明显混乱，且确认可以丢弃本地数据时，再执行完整清理：

```bash
docker compose down -v
make init
make start
```

## 5. API 如何单独配置

这里必须区分“后端运行时配置”和“前端构建时配置”两类参数，不能混写，否则最容易出现接口地址对不上、页面仍指向旧服务的问题。

### 5.1 后端运行时 API 配置

这些值由 `docker-compose.yml` 在容器启动时注入，主要影响后端生成的公开链接、SuperTokens 的 `apiDomain` 与 `websiteDomain`、媒体文件公开地址，以及后端访问 Vendure、SuperTokens 和 DeepSeek 的行为。

根目录 `.env` 可覆盖这些值：

```env
API_DOMAIN=http://127.0.0.1:3001
WEBSITE_DOMAIN=http://127.0.0.1:5178
SUPERTOKENS_API_KEY=
VENDURE_ADMIN_TOKEN=
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
ENABLE_DEV_AUTH_FALLBACK=true
```

如果后端对外地址发生变化，至少要同步调整 `API_DOMAIN` 与 `WEBSITE_DOMAIN`。

### 5.2 前端构建时 API 配置

前端不是在运行时动态读取这些地址，而是在构建镜像时通过 `VITE_*` 变量写入静态产物，因此修改后不能只重启容器，必须重新构建。

根目录 `.env` 可覆盖这些值：

```env
VITE_API_BASE_URL=http://127.0.0.1:3001/api
VITE_API_DOMAIN=http://127.0.0.1:3001
VITE_SOCKET_URL=http://127.0.0.1:3001
VITE_WEBSITE_DOMAIN=http://127.0.0.1:5178
```

修改这些值后，必须重新构建前端镜像：

```bash
docker compose build frontend
docker compose up -d frontend
```

### 5.3 当前实现上的优先级

当前前端逻辑已经调整为：优先使用 `VITE_API_BASE_URL`、`VITE_API_DOMAIN` 与 `VITE_WEBSITE_DOMAIN`，未配置时才根据浏览器地址推导本地默认值。因此，如果后续需要把项目交给他人复现，根目录 `.env` 应与源码一起提供，而不能只靠口头说明接口地址。

## 6. 哪些 ignore 文件要单独分发

后续向开发人员或自动化代理分发项目时，下面这些文件或目录虽然可能不在 Git 中，但对复现环境非常关键。

### 6.1 必须单独分发的配置文件

必须单独分发的配置文件包括根目录 `.env`、`backend/.env` 和 `vendure/.env`。其中，`backend/.env` 主要用于本机非 Docker 启动或脚本执行，`vendure/.env` 保存本地 Vendure 默认配置，而根目录 `.env` 是 Docker Compose 的统一覆盖入口，也是后续部署中最关键的配置文件。

### 6.2 不建议分发的数据目录

下面这些目录通常不应作为“源码配置”的一部分直接交付：

- `mysql-data/`
- `minio-data/`
- `meilisearch-data/`
- `supertokens-pg-data/`
- `vendure-data/`

这些目录保存的是运行时数据，而不是配置模板。

### 6.3 需要视场景决定的文件

`vendure-data/vendure.sqlite` 是否分发，需要看使用场景而定。如果希望保留当前 Vendure 状态，可以一并提供；如果只需要一套可重建环境，则无需分发，容器会重新生成。

## 9. 常见故障与处理

### 9.1 `db-init` 报 Prisma / OpenSSL 错误

先确认使用的是当前仓库中的最新 `backend/Dockerfile`。这一问题已经通过在镜像基础层安装 `openssl` 修复，旧镜像或旧缓存往往是问题来源。

### 9.2 `db-init` 报 `tsx: not found`

这通常说明初始化容器错误地使用了裁剪掉 dev 依赖的镜像。当前仓库已经调整为 `builder` 保留 dev 依赖供 `db-init` 使用，`runner` 再使用裁剪后的依赖供 `backend` 正式运行。

### 9.3 `vendure` 构建失败，提示 `better-sqlite3` 编译问题

这通常说明构建环境缺少 `python3`、`make` 和 `g++`。当前仓库中的 `vendure/Dockerfile` 已补齐这些依赖。

### 9.4 `frontend` 容器名冲突

若出现类似：

```text
Conflict. The container name "/swapcampus-frontend-1" is already in use
```

执行：

```bash
docker rm -f swapcampus-frontend-1
make start
```

### 9.5 改了根目录 `.env` 但前端地址没变

这通常不是配置没生效，而是因为前端地址属于构建时变量，修改后必须重新构建：

```bash
docker compose build frontend
docker compose up -d frontend
```

- `.env.example`
