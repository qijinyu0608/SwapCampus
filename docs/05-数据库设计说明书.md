# 数据库设计说明书

## 1. 数据库选型

系统当前采用“双库分工”的方式组织数据：业务主库使用 MySQL 8，负责承载用户、商品、订单、消息、校园服务、举报和信用中心等核心业务数据；认证与会话相关数据则由 SuperTokens 使用独立 PostgreSQL 保存。这样处理的原因很直接，一方面业务数据天然以结构化关系为主，适合通过 Prisma 配合 MySQL 做快速迭代；另一方面，把认证状态与业务表拆开，能避免课程项目后期在登录、会话和业务逻辑之间形成过深耦合。

## 2. 当前核心模型

当前主业务模型已经覆盖交易、沟通、治理和信用四类核心场景，主要包括：`User`、`StudentVerification`、`Product`、`ProductImage`、`Favorite`、`Order`、`OrderAppeal`、`Review`、`Conversation`、`Message`、`Report`、`AuditLog`、`UserBehavior`、`UserFollow`、`CampusServiceListing`、`CampusServiceImage`、`CampusServiceOrder`、`CampusServiceFavorite`、`CampusServiceBehavior`、`UserCreditAsset`、`CreditPointLedger`、`CreditMissionClaim` 和 `CreditRedeemOrder`。从当前代码结构看，这批表已经能够支撑课程设计要求中的主要业务闭环，而不是只停留在预留结构。

## 3. 关键枚举与状态

### 3.1 用户相关

用户侧主要枚举包括 `UserRole`、`VerificationStatus` 和 `AccountStatus`，分别用于区分普通用户与管理员、实名审核状态，以及账号是否处于正常或封禁状态。

### 3.2 商品交易相关

商品与交易相关状态主要由 `ProductStatus`、`OrderStatus`、`MessageType` 和 `BehaviorEventType` 约束。它们分别描述商品审核与上下架状态、订单推进状态、消息载荷类型，以及浏览、收藏、联系、下单等用户行为事件。

### 3.3 校园服务相关

校园服务侧的核心枚举包括 `CampusServiceIntent`、`CampusServiceCategory`、`CampusServiceListingStatus` 和 `CampusServiceOrderStatus`。这组状态设计的重点，是把“发布中的服务信息”和“围绕服务产生的订单过程”区分开来，便于同时支撑 `REQUEST` 与 `OFFER` 两种模式。

### 3.4 信用中心相关

信用中心当前围绕 `CreditPointChangeType`、`CreditPointSourceType` 和 `CreditRedeemOrderStatus` 组织积分变动来源、账本流向和兑换订单状态，已经具备基本的积分获取、消费和后台调整表达能力。

## 4. 主要关系设计

从关系设计上看，系统的数据中心仍然是 `User`。用户与商品是一对多，商品与图片是一对多；商品收藏通过 `Favorite` 实现用户与商品之间的多对多关系。订单围绕商品展开，一条订单可以继续挂接评价与申诉记录。消息系统采用 `Conversation + Message` 结构，把商品、订单和校园服务的沟通上下文统一收口到会话之下。校园服务方面，`CampusServiceListing` 负责发布信息，`CampusServiceOrder` 负责实际接单与履约过程。信用中心则以 `UserCreditAsset` 为账户聚合表，再向下延伸到账本、任务领取和兑换记录。

## 5. 主要表设计意图

### 5.1 `User`

`User` 表承载用户最核心的业务身份，包括角色、信用分、实名状态和账号状态，是多数业务关系的锚点。

### 5.2 `StudentVerification`

`StudentVerification` 用于保存实名补充信息，如真实姓名、学院、手机号和学生证材料，与 `User` 形成一对一关系。

### 5.3 `Product` / `ProductImage`

`Product` 与 `ProductImage` 共同描述商品发布内容，前者负责标题、描述、价格、分类、成色和状态，后者负责多图上传后的图片元数据与展示顺序。

### 5.4 `Favorite`

`Favorite` 已经是现行功能表，而不是预留结构。登录用户的商品收藏会持久化到该表，游客的临时想要仍只保存在浏览器本地。

### 5.5 `Order` / `Review` / `OrderAppeal`

`Order`、`Review` 和 `OrderAppeal` 负责支撑商品交易的后半段流程，使系统不仅能发布和浏览商品，还能沉淀成交、评价和争议处理记录。

### 5.6 `Conversation` / `Message`

`Conversation` 与 `Message` 采用统一消息结构，能够挂接商品、订单和校园服务等多种上下文，并支持 `ORDER_EVENT` 这类业务事件消息。

### 5.7 `CampusServiceListing` / `CampusServiceOrder`

`CampusServiceListing` 与 `CampusServiceOrder` 把校园服务拆成“发布内容”和“履约过程”两层，这样既能表达任务发布，也能表达服务供给，符合当前 `REQUEST / OFFER` 双向模型。

### 5.8 `CampusServiceFavorite`

`CampusServiceFavorite` 用于保存登录用户对校园服务发布的收藏关系。

### 5.9 `UserBehavior` / `CampusServiceBehavior`

`UserBehavior` 与 `CampusServiceBehavior` 用来记录浏览、收藏、联系、下单等行为，为推荐排序、运营统计和后续分析保留基础数据。

### 5.10 信用中心相关表

信用中心相关表包括 `UserCreditAsset`、`CreditPointLedger`、`CreditMissionClaim` 和 `CreditRedeemOrder`，分别对应积分账户聚合、流水明细、任务奖励领取和兑换记录。

## 6. 索引与约束

当前数据库约束主要围绕“身份唯一”“关系去重”和“高频查询路径”展开。`User.studentId` 与 `User.email` 保持唯一；`Favorite(userId, productId)`、`CampusServiceFavorite(userId, listingId)`、`UserFollow(followerId, followingId)` 都使用联合唯一约束，防止重复关系。针对首页、订单流和治理场景，`Product`、`Order`、`OrderAppeal`、`UserBehavior` 等表也已经按常见过滤条件建立索引，以保证常规查询性能和聚合统计效率。

## 7. 数据初始化口径

### 7.1 默认初始化

默认初始化只负责结构建表与必要检查，逻辑入口位于 `backend/prisma/init.ts`。当前口径下，执行初始化不会自动写入演示商品、订单、消息或校园服务数据。

### 7.2 可选演示种子

如需快速重建可演示环境，可执行：

```bash
npm run db:reset-and-seed-demo
```

脚本会调用 `backend/prisma/demo-seed.ts` 中的演示数据计划。按当前实现，演示种子规模为用户 10 条、商品 30 条、校园服务 18 条、商品订单 6 条、校园服务订单 4 条、举报 4 条、审计日志 3 条。

## 8. 当前文档口径

本文档中的“默认初始化结果”特指 `make init` 后的空库建表状态；“可选演示种子”特指手动执行 `db:reset-and-seed-demo` 后可复现的数据集。由于运行中的真实数据会随着注册、发布、下单和发消息持续变化，因此页面统计和业务数量不应在文档中写成固定不变的常量。

## 9. 当前实现结论

从当前实现看，商品收藏已经完成账号级落库，校园服务也已形成 `listing + order` 的双层建模。订单评价、申诉、关注关系、信用中心和媒体上传都有明确的数据承载结构。认证主事实仍位于 SuperTokens，但会话身份、角色与业务用户信息需要持续保持同步，这也是后续维护时必须注意的边界。
