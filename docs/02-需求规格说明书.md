# 需求规格说明书

## 1. 引言

SwapCampus 面向校内师生，围绕闲置商品交易、校园服务、站内沟通和后台治理构建统一系统。本说明书明确系统边界、用户角色、核心功能、非功能要求与数据口径，作为后续设计、实现和测试的共同依据。

## 2. 用户角色

系统主要分为三类使用者。游客可以浏览首页、商品详情和公开主页；普通用户在登录后可以注册、发布、收藏、下单、发消息并使用校园服务和信用中心；管理员负责审核、举报、申诉、用户治理和审计查看。

## 3. 核心需求

### 3.1 用户体系

用户体系需要支持学号或邮箱注册登录，支持实名补充信息和实名状态展示，能够对封禁账号做拦截，并允许用户维护个人资料。

### 3.2 商品能力

商品能力覆盖列表、搜索、详情、多图上传、发布规则读取、发布审核以及收藏与推荐联动。

### 3.3 交易能力

交易能力围绕线下面交展开，需要支持订单创建、状态流转、评价、申诉和订单快照查看。

### 3.4 消息能力

消息能力需要提供会话列表、消息明细、文本与附件发送，并支持基于 Socket.IO 的演示级实时推送。

### 3.5 校园服务能力

校园服务模块采用 `REQUEST / OFFER` 两种发布意图，支持服务发布、筛选、收藏、接单、完成，并与消息模块联动。

### 3.6 信用与成长能力

信用与成长能力主要体现在商品页、校园服务页和用户页的信用摘要展示，以及信用中心中的签到、任务、账本和奖励兑换。

### 3.7 后台治理能力

后台治理能力包括商品审核、举报处理、用户封禁与解封、实名审核、订单申诉处理和审计日志查看。

## 4. 非功能需求

系统还需要满足可复现部署、文档与代码同仓维护、后端测试和前端构建纳入 CI，以及页面可演示、可复现、可追溯等非功能要求。

## 5. 数据口径要求

数据口径分为两层：默认初始化只做空库建表，可选演示种子由脚本手动重建。运行中不断变化的数据不应写成固定常量。

## 6. 当前实现边界

消息模块暂未补齐已读回执、在线状态和断线补偿，会话治理还能继续增强，前端交互级自动化测试也仍有提升空间。
