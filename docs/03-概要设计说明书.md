# 概要设计说明书

## 1. 系统架构

系统采用前后端分离架构。前端使用 React + Vite，后端以 NestJS 业务主服务为核心，业务主库使用 MySQL，认证与会话交由 SuperTokens 承担，对象存储使用 MinIO，搜索由 Meilisearch 提供；同时，系统还通过 MySQL Outbox 派生出两个独立工作进程 `search-indexer` 与 `commerce-sync`，分别负责搜索索引收敛和 Vendure 异步同步。消息、推荐和治理虽然暂未拆为独立进程，但也已统一进入 Outbox 事件模型，并在单体内部用 consumer 收口副作用。

## 2. 设计原则

设计上坚持单体按领域模块拆分、文档与代码同仓维护、部署可通过 Compose 复现，并尽量把认证、媒体、搜索、外围电商同步和交易主链路分层处理。对不属于主事务事实的副作用，优先通过事件外发和异步消费者解耦，减少请求链路耦合。

## 3. 核心模块

核心模块包括用户与认证、商品、订单与评价、收藏与行为、消息、校园服务、信用中心、举报和后台治理，以及作为基础设施层的 `outbox`、`search-indexer`、`commerce-sync` 三部分。当前 `outbox` 除了服务搜索和外围电商同步，也承担消息生命周期、推荐行为、治理审计三类内部事件流。

## 4. 当前关键实现特征

商品发布已经接入图片上传、对象存储和内容审核，登录用户收藏已持久化到 `Favorite` 表，校园服务采用 `listing + order` 的双层模型，订单支持评价、申诉、快照和会话联动，消息支持会话鉴权与 Socket.IO 房间推送，信用中心支持签到、任务、账本和兑换；同时，商品、订单、卖家状态变化已经接入 Outbox 事件外发，搜索索引与 Vendure 同步改由独立工作进程异步收敛。消息发送、收藏/浏览/联系行为和治理审计也已经完成第一阶段事件化，当前仍由单体内 consumer 消费。

## 5. 部署概要

部署层面，默认运行态会同时启动 `backend`、`search-indexer`、`commerce-sync` 三个后端相关进程；其中消息、推荐、治理事件当前仍由 `backend` 进程内 consumer 处理。`db-init` 只负责建表，不自动导入演示数据；需要演示环境时，可通过 `db:reset-and-seed-demo` 重建；历史搜索事件缺失时，还可通过 `db:backfill-search-outbox` 补投；前端构建产物由 `nginx` 托管。

## 6. 当前边界

实时消息仍属于演示级能力，虽然已补齐消息生命周期事件和会话已读游标基础表，但完整未读回执、在线状态和断线补偿还可以继续增强；推荐画像当前只完成行为沉淀与轻量聚合，尚未独立实现召回、排序与推荐任务；治理事件当前已完成审计收口，但仍未引入独立 admin-audit 进程。事件驱动部分当前统一采用基于 MySQL 的 Outbox 轮询方式，已满足当前交付要求，但在监控、告警和人工补偿方面仍有提升空间。
