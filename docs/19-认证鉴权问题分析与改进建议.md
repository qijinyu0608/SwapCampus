这意味着当前系统已经完成了最核心的一次授权边界收口。

## 3. 本轮整改对应的问题结论

对原问题判断的更新如下：

### 3.1 “身份可信度依赖前端”问题已明显缓解

当前用户身份已由后端签发 JWT 并在守卫中校验，前端本地存储不再单独构成可信身份来源。

### 3.2 “token 没进入真实链路”问题已解决

当前 token 已真实进入：

- 登录返回
- 本地持久化
- 请求头注入
- 后端守卫解析
- 管理端与多条核心业务写链路授权判断

### 3.3 “管理员演示后门”问题已解决

当前登录页不存在硬编码管理员直通逻辑，管理员需通过真实账号登录。

### 3.4 “客户端显式传身份参数”问题已部分解决

写接口中的高风险身份参数已大幅收口，但仍有部分读接口延续旧模式，尚未完全归零。

## 4. 尚未完成的剩余事项

以下内容仍建议继续推进：

### 4.1 继续清理读接口中的 `userId` 参数

目前仍有部分读取型接口保留 `userId` 查询参数口径，例如：

- 推荐列表
- 商品详情
- 订单列表
- 某些演示辅助链路

这些接口虽然风险低于写接口，但从一致性和答辩口径上看，仍建议继续改为服务端从 token 中推导当前用户。

### 4.2 `messages/demo-hydrate` 仍属于演示辅助接口

该接口当前已收口为“登录后、开发态、仅对当前会话用户补水”的内部接口。  
后续如果项目进入更严格的交付口径，建议把这类“演示专用能力”进一步收口、隔离或移除。

### 4.3 尚未实现 refresh token

当前系统已具备：

- access token
- 401 清理本地会话
- 登出清理本地状态

但尚未具备：

- refresh token
- 续签接口
- token 轮换策略

### 4.4 文档与 README 仍需同步校正

凡是仍把系统描述为“mock token / 演示态登录”的文档，都应继续同步修订，避免代码已经整改、文档却还停留在旧结论。

## 5. 建议答辩表述

若老师追问“JWT 怎么校验、管理员如何授权、如何防前端篡改 role”，当前可按以下口径回答：

1. 项目已从演示态登录改为真实认证会话，后端负责建立与校验登录态
2. 前端统一保存 `accessToken`，并通过请求拦截器自动附加 `Authorization`
3. 管理端接口统一挂载 `JwtAuthGuard` 和角色守卫，只允许管理员访问
4. 商品发布、下单、消息、举报、校园服务等关键写操作，已不再依赖前端传 `sellerId`、`buyerId`、`handledBy` 等身份字段
5. 当前剩余工作主要是进一步清理少量读接口参数和补 refresh token，不影响核心鉴权闭环成立
