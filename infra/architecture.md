# 系统架构与工程设计说明

## 1. 架构目标
SwapCampus 在课程设计语境下优先解决三个问题：
- 让老师能看到完整业务闭环，而不是静态页面拼接
- 让部署和演示环境可重复构建，而不是依赖本机偶然状态
- 让系统具备继续演进到更高并发、更强治理能力的架构基础

## 2. 当前架构分层
### 2.1 表现层
- `frontend` 负责页面渲染、表单校验、用户状态缓存和接口调用
- 页面划分为首页、登录、发布、消息、个人中心、后台六个核心路由

### 2.2 应用层
- `backend` 基于 NestJS 提供 REST API
- 控制器负责路由和参数接收
- 服务层负责业务规则、状态流转和数据转换

### 2.3 数据层
- Prisma 作为数据访问抽象层
- MySQL 作为事务型业务数据库
- MinIO 作为对象存储预留层，当前用于后续图片上传能力扩展

## 3. 解耦设计
### 3.1 前后端解耦
- 前端只通过 `/api` 接口访问后端，不直接依赖数据库
- 前端通过 `services/api.ts` 统一封装 HTTP 请求，避免页面直接散落接口地址

### 3.2 控制器与服务解耦
- 控制器不直接访问 Prisma
- 服务层集中处理商品状态、订单创建、消息发送、后台审核等业务逻辑
- 这种结构便于后续补测试、补缓存、补消息队列，而不影响路由层

### 3.3 存储与业务解耦
- 业务代码通过 Prisma Client 访问数据，不直接拼接 SQL
- 后续如果需要增加读写分离、查询优化或缓存层，可优先在服务层和数据访问层演进

## 4. 事件驱动思想
当前交付版主要以同步 HTTP 为主，但在业务设计上已经预留事件驱动演进路径。

### 4.1 已体现的事件源
- 用户注册成功
- 商品发布成功
- 订单创建成功
- 消息发送成功
- 商品审核状态变更

### 4.2 推荐事件模型
可定义如下领域事件：
- `UserRegistered`
- `ProductPublished`
- `OrderCreated`
- `MessageSent`
- `ProductStatusChanged`

### 4.3 事件驱动的价值
- 发送消息后可异步触发通知
- 商品审核后可异步刷新搜索索引
- 注册后可异步初始化用户画像或风控记录
- 订单创建后可异步沉淀交易日志和推荐特征

## 5. 消息队列与异步化预案
当前版本未强行引入 MQ，是因为课程设计交付优先级高于复杂基础设施引入。但架构上已适合继续扩展：
- 推荐接入 Redis Stream / RabbitMQ / Kafka 中的一种
- 后端服务层在关键业务成功后发布领域事件
- 通知、审核日志、推荐计算、搜索索引更新等作为异步消费者处理

这样做的收益：
- 降低主请求链路时延
- 减少功能耦合
- 为并发增长预留缓冲能力

## 6. IaC 思路
当前项目的基础设施即代码体现在：
- 使用 `docker-compose.yml` 描述 MySQL、MinIO、backend、frontend 四个服务
- 使用 `Makefile` 收敛安装、启动、构建和测试命令
- 使用 Prisma Schema 作为数据库结构定义

这意味着：
- 新环境可按统一方式启动
- 服务、端口、依赖关系和环境变量具备可追溯性
- 数据库结构变更可通过 schema 管理，而不是手工点改

## 7. CI/CD 设计
### 7.1 当前已落地资产
- `.github/workflows/ci.yml`
- 后端执行 `npm test -- --runInBand`
- 前端执行 `npm run build`

### 7.2 CI 目标
- 保证每次提交至少通过基础测试和构建
- 防止“文档更新了但代码不可构建”的交付事故

### 7.3 CD 建议
课程设计阶段可不做自动生产发布，但建议保留如下思路：
- 合并到主分支后自动构建镜像
- 通过预发布环境执行容器化验收
- 在答辩环境或教学服务器上手工触发部署

## 8. 可维护性设计
- 前后端统一采用 TypeScript，降低接口字段理解成本
- 页面按路由拆分，业务 API 按服务集中封装
- 文档扁平目录管理，避免课程文档层级过深
- 开发记录与验收记录独立保存，方便追踪演进过程

## 9. 可用性设计
- 页面提供按钮、状态标签、提示信息和兜底文案
- 商品、消息、后台数据均来自真实数据库，不是纯静态 Mock
- 后端商品模块保留 fallback，避免数据库异常时首页完全空白
- Docker Compose 统一启动环境，降低演示失误率

## 10. 容量与并发估算
课程设计版本未做压测集群，但可以给出合理工程估算。

### 10.1 当前部署形态
- 单前端容器
- 单后端容器
- 单 MySQL 实例
- 单 MinIO 实例

### 10.2 适用场景
- 课程答辩演示
- 小规模校内试用
- 数十到数百注册用户
- 同时在线 20 到 50 人级别

### 10.3 粗略容量判断
在当前架构和未启用缓存/MQ 的前提下：
- 首页商品流、统计、消息查询、后台概览都属于轻量读请求
- 单实例后端对几十级并发请求具备可支撑性
- 如果请求量继续增加，数据库查询与同步写入会成为瓶颈

### 10.4 扩展方向
- 对首页统计增加 Redis 缓存
- 对消息通知、审核日志、推荐任务引入消息队列
- 将商品查询和订单写入拆分读写压力
- 引入 Nginx 反向代理和多实例后端

## 11. 架构结论
当前版本在课程设计范围内已经具备：
- 明确分层
- 可维护的模块边界
- 可复制的基础设施编排
- 可继续向事件驱动和高并发演进的设计基础

这满足“课程设计交付版”的工程性要求，也为后续迭代提供了清晰演进路径。
