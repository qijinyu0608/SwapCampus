# 用户数据结构规范

## 1. 目标

本文档定义 SwapCampus 当前和目标态的用户数据结构约束。

它用于解决两个问题：

1. 当前用户数据分散在 `User`、`StudentVerification`、登录态、资料页、信用摘要里，语义不够统一
2. 后续做 UI 重构、权限收口、资料改造时，需要一套稳定的用户域结构基线

本文档同时描述：

- 当前真实实现
- 当前不合理点
- 后续应修正到什么结构

## 2. 用户域分层

当前用户域建议按 4 层理解：

1. 账号主表
2. 身份与资料附表
3. 认证态 / 会话态
4. 前端读模型

## 5. 当前结构中的不合理点

### A. `name` 和 `realName` 语义混杂

当前问题：

- `User.name` 在产品语义上更像昵称 / 展示名
- `StudentVerification.realName` 才是真实姓名
- 但当前接口和页面有时会把两者混用

修正口径：

- `name` 明确为展示名 / 昵称
- `realName` 明确为实名信息
- 页面、接口、表单后续不得再混写

### B. `isVerified` 和 `verification.status` 同时表达认证语义

当前问题：

- `User.isVerified` 是布尔
- `StudentVerification.status` 是字符串状态
- 两者都在表达认证结果，容易不一致

修正口径：

- 数据库内部当前继续允许两者并存
- 外部接口统一只暴露 `verificationStatus`
- `isVerified` 仅视为内部派生/缓存字段，不得继续直接暴露给前端页面或前端类型

### C. 学院、手机号只存在附表里

当前问题：

- 用户基础信息和资料信息被拆开
- 资料页读取时必须依赖额外拼装

修正口径：

- 当前保持拆表不变
- 但前端读模型必须把它们收敛成稳定 `UserProfile`
- 页面层不应自行推断“待填写”等兜底逻辑

### D. 登录态和资料态字段不统一

当前问题：

- 登录态只有 `AuthUser`
- 资料页是 `UserProfile`
- 信用摘要又是 `UserTrustSummary`
- 字段命名和语义存在重复

修正口径：

- 允许多种读模型并存
- 但必须围绕统一核心字段扩展，而不是各写一套
- `name`、`verified`、`identityStatus` 不再允许出现在新的外部契约、前端会话结构和页面消费中

### E. 封禁状态没有前端统一读模型

当前问题：

- `isBanned` 已落库
- 但前端公开类型里没有稳定暴露这一语义

修正口径：

- 管理端读模型应明确暴露账号状态
- 用户域规范中应明确 `accountStatus` 是可持续扩展的概念

## 7. 当前阶段的明确约束

### 7.1 命名约束

- `name` 视为展示名
- `realName` 视为实名姓名
- `verified` / `isVerified` 只用于兼容旧结构
- `identityStatus` / `verificationStatus` 代表认证流程状态
- 对外字段名统一使用 `displayName / verificationStatus / accountStatus`

### 7.2 认证约束

- 权限判断只依赖认证态中的 `id` 和 `role`
- 页面展示实名信息时，应从资料 / 认证模型读取，不从登录态推断

### 7.3 资料约束

- 学院、手机号、真实姓名属于资料层，不属于登录态最小结构
- 未填写时由服务层给出统一兜底，不在多个页面重复写默认文案

### 7.4 治理约束

- 封禁状态是账号治理语义，不是资料语义
- 信用分是长期统计语义，不应混进登录态最小结构作为必需字段

### 7.5 强制外部契约约束

- 对外接口不得继续返回 `name` 作为用户展示字段
- 对外接口不得继续返回 `verified`
- 对外接口不得继续返回 `identityStatus`
- 前端 session、profile、public user、admin user、message hydrate 等结构必须共享统一口径

## 8. 与当前代码的映射

当前关键实现点：

- 数据库：`backend/prisma/schema.prisma`
- 认证态：`backend/src/modules/auth/auth.types.ts`
- 资料与信用摘要：`backend/src/modules/users/users.service.ts`
- 前端登录态与 API 类型：`frontend/src/services/api.ts`

这些文件是用户域重构时的高敏感区域。

## 9. 后续修正顺序建议

建议按以下顺序推进：

1. 统一 `name / realName` 语义
2. 统一 `verified / identityStatus / verificationStatus` 口径
3. 为前端补稳定的 `UserProfile` 与 `UserTrustSummary` 类型
4. 管理端显式引入账号状态表达
5. 再决定是否进一步调整数据库字段

## 10. 结论

当前用户结构能跑通业务，但不是理想终态。

后续用户域重构最重要的是三件事：

1. 账号、资料、认证、信用四层语义分开
2. 命名统一
3. 不再让页面自己拼用户真相

这三点落实后，后续 UI 和权限体系都会稳定很多。
