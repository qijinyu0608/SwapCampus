# 商品数据结构规范

## 1. 目标

本文档定义 SwapCampus 商品域的数据结构基线，用于支撑后续 UI 全面重构、接口扩展、推荐排序、审核治理和图片上传改造。

目标不是只描述当前已经实现的字段，而是给出一套：

- 当前实现可对齐
- 后续演进可落地
- 前后端可以共享语义
- 不因页面改版而反复漂移

的商品数据结构规范。

## 2. 设计原则

商品数据结构必须满足以下原则：

1. 商品主信息稳定
2. 分类体系单一事实源
3. 审核状态、交易状态、展示状态语义清晰
4. 图片、标签、扩展属性、统计信号独立建模
5. 列表摘要和详情结构有明确分层
6. 允许当前版本先保留简化实现，但文档口径必须完整

## 3. 当前已实现的核心落库结构

当前 Prisma 中商品相关表如下：

- `Product`
- `ProductImage`
- `Favorite`
- `Order`
- `Report`
- `UserBehavior`

当前 `Product` 已落库字段：

| 字段 | 类型 | 当前状态 | 说明 |
| --- | --- | --- | --- |
| `id` | `Int` | 已实现 | 商品 ID |
| `sellerId` | `Int` | 已实现 | 发布者 ID |
| `title` | `String` | 已实现 | 商品标题 |
| `description` | `String` | 已实现 | 商品描述 |
| `price` | `Decimal(10,2)` | 已实现 | 售价 |
| `category` | `String` | 已实现 | 主分类中文名 |
| `condition` | `String` | 已实现 | 成色文案 |
| `tags` | `String` | 已实现 | 逗号分隔标签串 |
| `status` | `ProductStatus` | 已实现 | `PENDING / ON_SALE / SOLD / OFFLINE` |

当前相关能力：

- 收藏、订单、举报、行为埋点已与商品关联
- 前端已有 `ProductSummary`、`ProductDetail` 两层读取模型

## 4. 当前结构的主要不足

当前结构可运行，但对后续系统性重构仍有明显限制：

1. `category` 仍是字符串，尚未枚举化
2. `condition` 是自由文案，不利于筛选和统计
3. `tags` 是逗号字符串，不利于去重、搜索和治理
4. `status` 同时承担审核、展示、交易三层语义，扩展性一般
5. 缺少图片上传来源、封面图、媒体类型等元数据
6. 缺少运费/交付方式/面交范围等交易表达
7. 缺少合规字段，如自动审核命中、白名单命中、风险等级
8. 缺少结构化规格字段，如品牌、型号、版本、容量

因此后续应采用“当前实现结构 + 目标规范结构”的双层口径。

## 4.1 当前不合理点与修正口径

以下问题不再视为“可长期接受的实现细节”，后续应按明确方向修正：

### A. `category` 仍是自由字符串

当前问题：

- 数据库存的是 `String`
- 创建商品 DTO 也是 `string`
- 只能依赖服务层做归一化

修正口径：

- 当前阶段允许数据库继续存中文分类名
- 但输入口必须只接受主分类集合，不再接受任何历史别名
- 前后端类型应逐步收敛到 `ProductCategoryName`
- 历史错误分类值应通过清理脚本和迁移脚本一次性修正
- 业务主流程、表单、接口、推荐、筛选、首页入口中不得继续出现历史别名

### B. `condition` 仍是自由文案

当前问题：

- 不利于筛选
- 不利于排序
- 不利于推荐画像和统计

修正口径：

- 当前 UI 仍展示中文文案，但输入口必须只接受受控集合
- 当前唯一合法值为：`95新 / 9成新 / 8成新`
- 不再接受自由输入成色
- 后续数据库升级时再拆为 `conditionCode + conditionLabel`

### C. `tags` 落库为逗号字符串

当前问题：

- 页面读取前必须二次拆分
- 标签类型无法治理
- 容易出现重复、空值、脏值

修正口径：

- 外部接口唯一合法类型为 `string[]`
- 页面状态、DTO、前端服务类型、测试数据一律按 `string[]` 组织
- 数据库存储层当前允许继续使用逗号字符串，但这只是持久化细节，不是领域契约
- 任何新逻辑不得再以“输入字符串标签”为前提
- 中期应升级为数组或独立表，不再新增基于字符串拼接的逻辑

### D. `status` 承担过多语义

当前问题：

- 同时承担审核态、展示态、交易态
- 未来扩展会变得模糊

修正口径：

- 当前版本继续沿用 `PENDING / ON_SALE / SOLD / OFFLINE`
- 但文档上明确这是“简化生命周期状态”
- 新增业务若需要更细治理，不允许继续往同一个字段里硬塞新语义

### E. 媒体结构过弱

当前问题：

- 只有 `imageUrl`
- 没有封面字段
- 没有来源、尺寸、MIME 等元信息

修正口径：

- 当前仍可使用 `ProductImage`
- 但后续图片上传和对象存储闭环必须以增强媒体结构为目标

### F. 发布载荷过于简化

当前问题：

- 没有媒体
- 没有交易方式
- 没有扩展属性
- 没有结构化标签

修正口径：

- 当前发布载荷继续服务现有页面，但它只是一版受限输入模型
- 当前最低约束为：
  - `category` 必须属于分类规范主分类
  - `condition` 必须属于受控成色集合
  - `tags` 必须为字符串数组
- 不再兼容旧的 `tags: string` 或历史分类别名输入

## 5. 商品域目标结构总览

后续商品域建议按 6 个层面建模：

1. 商品主表 `Product`
2. 商品媒体 `ProductMedia`
3. 商品标签 `ProductTag`
4. 商品扩展属性 `ProductAttribute`
5. 商品统计快照 `ProductMetrics`
6. 商品审核与治理信息 `ProductCompliance`

其中：

- `Product` 是主聚合根
- 其余结构应作为附属表或派生读模型
- 列表页、详情页、推荐流各自读取不同层次的数据

## 6. 商品主表规范

### 6.1 必备字段

以下字段应视为商品主表长期稳定字段：

| 字段 | 类型建议 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `Int` | 是 | 商品 ID |
| `sellerId` | `Int` | 是 | 发布者 ID |
| `title` | `String(120)` | 是 | 商品标题 |
| `description` | `Text` | 是 | 商品描述 |
| `category` | `ProductCategoryName` | 是 | 主分类，受 [23-商品分类体系规范.md](/home/th1rt3en/dev/forge/SwapCampus/agent/domain/23-商品分类体系规范.md) 约束 |
| `conditionCode` | `enum` | 是 | 成色枚举 |
| `conditionLabel` | `String` | 是 | 成色展示文案 |
| `price` | `Decimal(10,2)` | 是 | 售价 |
| `originalPrice` | `Decimal(10,2)` | 否 | 原价或参考价 |
| `status` | `ProductLifecycleStatus` | 是 | 商品生命周期状态 |
| `saleMode` | `enum` | 是 | 普通售卖 / 免费送 / 可交换 |
| `deliveryMethods` | `set/json` | 是 | 面交 / 自提 / 校内送达 |
| `campusScope` | `String` | 否 | 可交易校区或地点范围 |
| `publishedAt` | `DateTime` | 是 | 实际上架时间 |
| `createdAt` | `DateTime` | 是 | 创建时间 |
| `updatedAt` | `DateTime` | 是 | 更新时间 |

### 6.2 建议枚举

#### 成色枚举 `conditionCode`

建议固定为：

- `NEW`
- `LIKE_NEW`
- `GOOD`
- `FAIR`
- `USED`

前端展示文案可映射为：

- `全新`
- `95新`
- `9成新`
- `8成新`
- `有明显使用痕迹`

#### 销售模式 `saleMode`

- `SELL`
- `FREE`
- `EXCHANGE`

说明：

- `免费送` 和 `交换` 是交易方式，不是主分类
- 当前如果数据库暂未拆字段，也应通过标签或表单值保留该语义

#### 生命周期状态 `ProductLifecycleStatus`

若未来拆细状态，建议替代当前单一 `status`：

- `DRAFT`
- `PENDING_REVIEW`
- `REJECTED`
- `ON_SALE`
- `LOCKED`
- `SOLD`
- `OFFLINE`
- `DELETED`

当前版本可继续使用：

- `PENDING`
- `ON_SALE`
- `SOLD`
- `OFFLINE`

但文档上应明确它属于“简化状态模型”。

## 7. 商品媒体结构

当前已有 `ProductImage`，后续建议提升为更完整的媒体结构：

| 字段 | 类型建议 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `Int` | 是 | 媒体 ID |
| `productId` | `Int` | 是 | 商品 ID |
| `mediaType` | `enum` | 是 | `IMAGE` / `VIDEO` |
| `url` | `String` | 是 | 资源地址 |
| `thumbnailUrl` | `String` | 否 | 缩略图 |
| `width` | `Int` | 否 | 宽度 |
| `height` | `Int` | 否 | 高度 |
| `sizeBytes` | `Int` | 否 | 文件大小 |
| `mimeType` | `String` | 否 | 媒体类型 |
| `storageProvider` | `String` | 否 | 本地 / MinIO / OSS |
| `sortOrder` | `Int` | 是 | 顺序 |
| `isCover` | `Boolean` | 是 | 是否封面 |
| `createdAt` | `DateTime` | 是 | 创建时间 |

当前阶段最低演进要求：

1. 保留 `sortOrder`
2. 明确第一张图是否为封面
3. 为接入对象存储预留来源字段

## 8. 商品标签结构

当前 `Product.tags` 是逗号分隔字符串，只适合演示，不适合作为长期结构。

目标规范建议：

### 8.1 标签分类

- 交易标签：`免费送` `可交换` `同校面交`
- 时效标签：`今天可取` `急出`
- 场景标签：`考研` `桌搭` `通勤`
- 合规标签：`宿舍白名单`
- 内容标签：`原箱` `带配件` `几乎未用`

### 8.2 存储建议

可选两种方案：

1. 中间表 `ProductTag(productId, tagCode, tagLabel, tagType)`
2. 若短期不拆表，至少改为 `string[]` 或 JSON 数组

不建议长期保留逗号字符串，因为它会带来：

- 去重困难
- 查询困难
- 标签类型无法治理
- 统计口径不稳定

## 9. 商品扩展属性结构

不同主分类需要不同的规格字段，因此建议引入扩展属性层：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | `Int` | 主键 |
| `productId` | `Int` | 商品 ID |
| `attributeKey` | `String` | 属性键，如 `brand` `model` `color` `capacity` |
| `attributeLabel` | `String` | 属性展示名 |
| `attributeValue` | `String` | 属性值 |
| `sortOrder` | `Int` | 展示顺序 |

分类示例：

- 数码电子：`brand` `model` `storage` `batteryHealth`
- 教材资料：`courseName` `edition` `hasNotes`
- 宿舍生活：`size` `material` `powerType`
- 鞋服箱包：`size` `gender` `season`
- 卡券票务：`expireAt` `usableScope` `faceValue`

这样可以避免把所有类目特有字段硬塞进 `Product` 主表。

## 10. 商品审核与治理结构

对于校园交易场景，合规字段应被明确定义，而不是散落在规则文案里。

建议结构：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `reviewStatus` | `enum` | 审核状态 |
| `reviewReason` | `String` | 驳回或处理原因 |
| `reviewedBy` | `Int` | 审核人 |
| `reviewedAt` | `DateTime` | 审核时间 |
| `riskLevel` | `enum` | `LOW / MEDIUM / HIGH` |
| `hitRules` | `json/string[]` | 命中的自动审核规则 |
| `isDormWhitelistItem` | `Boolean` | 是否宿舍白名单物品 |
| `isReportedSensitive` | `Boolean` | 是否高风险举报商品 |

当前系统里：

- 自动审核规则存在于 `ProductsService`
- 但审核命中结果未结构化落库

这部分是后续治理升级的重要基础。

## 11. 商品统计信号结构

前端详情页、推荐页、运营页都会依赖商品信号，因此建议从一开始就固定统计语义。

建议标准字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `viewCount` | `Int` | 浏览数 |
| `favoriteCount` | `Int` | 收藏数 |
| `contactCount` | `Int` | 发起沟通数 |
| `orderCount` | `Int` | 下单次数 |
| `reportCount` | `Int` | 举报次数 |
| `conversionScore` | `Float` | 综合转化分 |
| `heatScore` | `Float` | 热度分 |

说明：

- `viewCount`、`favoriteCount`、`reportCount` 应有可审计来源
- `heatScore` 和 `conversionScore` 可以是派生值，不必直接暴露给前端

## 12. 前端读模型规范

前端至少应稳定维护三种读模型。

### 12.1 列表卡片 `ProductSummary`

适用于首页、收藏页、推荐流、个人发布列表。

建议字段：

- `id`
- `title`
- `coverImageUrl`
- `category`
- `conditionLabel`
- `price`
- `status`
- `summaryTags[]`
- `sellerName`
- `sellerVerified`
- `sellerCreditScore`
- `favoriteCount`
- `isFavorited`
- `recommendationReason`

### 12.2 详情模型 `ProductDetail`

适用于商品详情页。

在 `ProductSummary` 基础上增加：

- `description`
- `images[]`
- `attributes[]`
- `deliveryMethods[]`
- `campusScope`
- `publishedAt`
- `seller`
- `stats`
- `compliance`
- `relatedProducts[]`

### 12.3 发布载荷 `ProductCreatePayload`

建议字段：

- `title`
- `description`
- `category`
- `conditionCode`
- `price`
- `saleMode`
- `tags[]`
- `deliveryMethods[]`
- `campusScope`
- `images[]`
- `attributes[]`

当前前端 `ProductCreatePayload` 仍是简化版：

- `title`
- `description`
- `price`
- `category`
- `condition`
- `tags`

说明后续发布表单仍有较大扩展空间。

## 13. 后端接口契约建议

### 13.1 创建商品

`POST /api/products`

最少应校验：

- 标题非空且长度合理
- 分类必须属于主分类集合
- 成色必须属于允许枚举
- 价格必须大于等于 0
- 标签数量和长度受控
- 交易方式不能污染主分类

### 13.2 商品列表

`GET /api/products`

建议支持的查询维度：

- `category`
- `tags`
- `keyword`
- `conditionCode`
- `minPrice`
- `maxPrice`
- `saleMode`
- `status`
- `sort`

### 13.3 商品详情

`GET /api/products/:id`

返回结构应明确区分：

- 商品主体
- 卖家信息
- 统计信息
- 合规信息
- 相关推荐

## 14. 数据库演进建议

在不影响当前演示系统运行的前提下，建议按以下顺序推进：

1. 将 `Product.category` 全量迁移为冻结主分类
2. 将 `condition` 从自由文本收敛为枚举值加展示文案
3. 将 `tags` 从逗号字符串升级为数组或独立表
4. 为 `ProductImage` 增加封面和来源元数据
5. 拆分审核状态与交易状态
6. 引入扩展属性结构
7. 为筛选、推荐和统计增加必要索引

## 15. 最小必做索引建议

当前与后续应重点保证以下索引：

- `Product(sellerId)`
- `Product(status, createdAt)`
- `Product(category, status)`
- `Product(price, status)` 或按查询量补充
- `ProductImage(productId, sortOrder)`
- `Favorite(productId, createdAt)`
- `ProductTag(productId, tagCode)` 若拆标签表

## 16. 与当前实现的对应关系

当前代码中已存在的关键读模型与入口：

- 前端类型：`frontend/src/services/api.ts`
  - `ProductSummary`
  - `ProductDetail`
  - `ProductCreatePayload`
- 后端实现：`backend/src/modules/products/products.service.ts`
  - `buildProductCards()`
  - `getProductDetail()`
  - `createProduct()`
- 数据库结构：`backend/prisma/schema.prisma`

这意味着后续重构可以在现有基础上演进，而不是推倒重来。

## 17. 结论

对 SwapCampus 而言，商品数据结构应当稳定为：

- 主表承载稳定业务主信息
- 分类冻结并统一入口
- 标签、图片、扩展属性、统计信号独立表达
- 列表、详情、发布载荷分层清晰
- 当前实现允许简化，但未来目标结构必须先写清楚

这样后续做 UI 大重构时，页面可以换，数据语义不用再反复返工。
