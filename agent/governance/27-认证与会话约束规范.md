# 认证与会话约束规范

## 1. 目标

本规范定义 SwapCampus 当前唯一有效的认证、会话与权限基线。

目的只有一个：

- 不再允许前端本地伪 session、演示用户覆盖真实登录态
- 不再允许业务页面自行拼装“当前用户真相”
- 不再允许同一账号在业务库与认证库之间出现邮箱、角色、身份不一致

## 2. 当前唯一认证基线

当前项目统一使用：

- `SuperTokens` 负责认证凭证、session 与角色 recipe
- `backend/prisma/schema.prisma` 中的 `User` 表负责业务用户主档
- `supertokensUserId` 作为认证账号与业务用户的唯一关联键

结论：

- 认证真相来自 `SuperTokens session`
- 业务真相来自 `User` / `StudentVerification`
- 前端 localStorage 只能缓存当前登录用户快照，不能伪造认证

## 3. 强制约束

### 3.1 前端约束

- 前端当前登录用户统一使用 `frontend/src/services/session.ts` 中的 `SessionUser`
- 前端认证状态统一通过 `frontend/src/services/auth-state.tsx` 提供
- 页面、组件、服务层不得再定义 `DemoUser`、`MockUser`、`LocalUser`
- 页面不得再通过 `saveDemoUser`、`getDemoUser`、`clearDemoUser` 一类旧接口维护登录态
- 页面不得在消息补水、演示数据注入等流程中篡改当前登录用户 `id`

### 3.2 路由约束

- 需要普通用户权限的页面统一通过 `RequireUser` 保护
- 需要管理员权限的页面统一通过 `RequireAdmin` 保护
- 页面内部可以保留更细的交互禁用，但不得替代路由层权限边界

### 3.3 读接口约束

- 订单列表、会话列表、收藏列表等“当前用户视角”接口，不再接受前端显式 `userId` 作为当前身份
- 这类接口必须直接从认证态推导当前用户
- 若接口同时需要支持公开视角和登录视角，应拆分为两个清晰口径，而不是混用 query 参数冒充登录态

### 3.4 后端约束

- 写接口中的身份必须从 session 解析，不得继续信任前端传入 `userId` / `sellerId` / `buyerId`
- 读接口若需要“当前用户是否收藏 / 是否有权限”等派生信息，应优先从可选 session 解析
- 修改用户邮箱、角色等认证关键字段时，必须同步到 `SuperTokens`

### 3.5 实时连接约束

- WebSocket 握手必须携带 `SuperTokens access token`
- Socket 服务端必须在握手阶段校验 session
- 客户端加入私有会话房间前，服务端必须再次校验该用户是否为会话参与者

### 3.6 部署约束

- Docker 默认认证 Core 为自托管 `http://supertokens:3567`
- 不再把 `https://try.supertokens.com` 作为默认开发/运行口径
- 演示补水能力默认关闭，只有显式设置 `ENABLE_MESSAGE_DEMO_HYDRATE=true` 与 `VITE_ENABLE_MESSAGE_DEMO_HYDRATE=true` 时才允许启用

## 4. 当前关键实现落点

- 前端会话缓存：`frontend/src/services/session.ts`
- 前端认证状态：`frontend/src/services/auth-state.tsx`
- 前端登录配置：`frontend/src/services/auth.ts`
- 前端路由保护：`frontend/src/router/guards.tsx`
- 后端认证服务：`backend/src/modules/auth/*`
- 用户资料更新与认证同步：`backend/src/modules/users/users.service.ts`
- Docker 认证 Core 配置：`docker-compose.yml`

## 5. 禁止回退项

以下做法视为错误回退：

- 为了演示方便重新引入 `DemoUser`
- 在 localStorage 里单独维护一套“游客 / 假登录用户”覆盖真实 session
- 在消息补水接口返回后直接把前端当前用户改成另一个用户 ID
- 在新页面里重新通过 query/body 传 `userId` 代表当前登录用户

## 6. 后续改造优先级

后续认证优化按以下顺序推进：

1. 清理剩余读接口里的 `userId` 显式传参
2. 为 WebSocket 接入 session / socket 认证
3. 视需要补 refresh / rotation 策略
4. 再考虑更细粒度 capability / permission 模型
