# 实现架构与模块职责基线

## 1. 目的

本文档用于收敛当前 SwapCampus 的实现层结构约束，给后续重构提供一个稳定的架构基线。

它回答的是：

- 代码应该怎么分层
- 模块边界应该怎么守
- 规则应该放在哪里
- 哪些职责不能重新散回页面

## 2. 当前实现分层

当前项目采用前后端分离结构：

- 前端：`frontend/`
- 后端：`backend/`
- 文档：`docs/` 与 `agent/`
- 基础设施：`docker-compose.yml`、`Makefile`、`infra/`

## 3. 前端结构基线

当前前端目录边界如下：

- `frontend/src/pages`
  - 页面路由级容器
- `frontend/src/components`
  - 可复用 UI 组件和领域组件
- `frontend/src/services`
  - API 调用、会话、行为记录等服务封装
- `frontend/src/constants`
  - 共享常量与统一入口定义
- `frontend/src/styles`
  - token、全局样式、legacy 样式
- `frontend/src/utils`
  - 纯工具函数

约束如下：

1. 页面负责组合，不负责沉淀底层规则
2. 接口地址、请求参数、响应转换集中在 `services`
3. 可复用常量集中在 `constants`
4. 样式 token 与共享视觉规则集中在 `styles`
5. 不在多个页面重复定义同一业务常量

## 4. 后端结构基线

当前后端目录边界如下：

- `backend/src/modules/auth`
- `backend/src/modules/products`
- `backend/src/modules/orders`
- `backend/src/modules/messages`
- `backend/src/modules/favorites`
- `backend/src/modules/recommendations`
- `backend/src/modules/reports`
- `backend/src/modules/users`
- `backend/src/modules/admin`
- `backend/src/modules/campus-services`

约束如下：

1. 控制器只负责路由、参数接收和权限入口
2. 服务层负责业务规则、状态流转、聚合与数据转换
3. DTO 负责输入校验边界
4. Prisma 结构定义集中在 `backend/prisma/schema.prisma`
5. 不允许控制器直接承载复杂业务逻辑

## 5. 规则收口原则

以下规则必须集中收口，不能重新散落：

### 5.1 商品分类规则

- 统一入口见 `agent/domain/23-商品分类体系规范.md`
- 前端和后端只从统一常量读取

### 5.2 商品发布规则

- 允许分类
- 禁售词
- 宿舍电器白名单
- 自动审核拒绝条件

这些规则必须以后端为准，前端只读取和展示。

### 5.3 商品数据转换

- price 转 number
- tags 字符串转数组
- category 归一化
- 列表卡片字段拼装

这些转换应集中在服务层或 API 层，不应散在各页面。

### 5.4 推荐逻辑

- 推荐理由生成
- 行为权重
- 热度排序

应集中在后端推荐/商品服务，不在前端拼装推荐规则。

## 6. 状态流转约束

后续重构不可破坏现有核心状态流。

### 6.1 商品状态

- `PENDING`
- `ON_SALE`
- `SOLD`
- `OFFLINE`

### 6.2 订单状态

- `PENDING`
- `IN_PROGRESS`
- `WAITING_REVIEW`
- `COMPLETED`
- `CANCELED`

### 6.3 校园服务状态

- `OPEN`
- `MATCHED`
- `DONE`
- `CANCELED`

如果后续要扩展状态，必须先更新 `agent/` 规范，再同步实现。

## 7. 页面与数据分离原则

前端页面允许大改，但必须遵守：

1. 页面不直接定义商品主结构
2. 页面不直接定义审核规则
3. 页面不直接拼接口 URL
4. 页面不直接复制分类体系
5. 页面不直接保存与后端不一致的状态语义

## 8. 共享组件边界

当前应逐步推动共享组件承担更多稳定表达，尤其是：

- 顶部导航
- 商品摘要卡
- 折叠区
- 数据展示块
- 共享表单结构

但共享组件不应承担页面级业务编排。

## 9. 兼容与渐进重构原则

当前项目存在 legacy 样式和历史实现，因此结构重构采用渐进式原则：

1. 先统一单一事实源
2. 再统一共享组件与类型
3. 最后清理 legacy 实现

不要求一轮内把所有历史结构全部推倒。

## 10. 与当前代码的直接映射

当前最关键的结构收口点：

- 分类入口：`frontend/src/constants/productCategories.ts`
- API 类型：`frontend/src/services/api.ts`
- 商品服务：`backend/src/modules/products/products.service.ts`
- 数据库模型：`backend/prisma/schema.prisma`
- 全局 token：`frontend/src/styles/tokens.css`

这些文件应被视为后续重构的高敏感区域。

## 11. 结论

后续任何大重构都应遵守一个基本原则：

> 页面可以重写，样式可以重写，组件可以重组，但规则、状态、分类和数据语义不能重新散开。

这就是当前实现架构基线的核心意义。
