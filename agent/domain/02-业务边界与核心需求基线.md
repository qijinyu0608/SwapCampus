# 业务边界与核心需求基线

## 1. 目的

本文档用于把旧的需求规格说明收敛成当前仍有效的业务边界基线。

它不再复述课程设计式的大而全需求，而只保留对后续重构仍然有约束力的部分：

- 这个产品到底是什么
- 这个产品不是什么
- 哪些能力必须长期保留
- 哪些边界不能被 UI 改版破坏

## 2. 产品定位

SwapCampus 的定位固定为：

> 面向校内师生的、以同校近场面交为核心的校园闲置交易平台。

该定位包含四个关键约束：

1. 用户范围以校内师生为主
2. 交易方式以线下面交为主
3. 平台强调信用、实名、审核和治理
4. 商品范围聚焦校园高频闲置，不做泛社会化二手平台

## 3. 明确不做的事情

后续无论 UI 如何重构，都不应把系统演进成以下方向：

- 泛电商平台
- 线上支付平台
- 全国物流寄售平台
- 不受校园规则约束的自由市场
- 把跑腿、代办、拼单混入普通商品主流的混合平台

## 4. 核心业务闭环

SwapCampus 必须长期保留的最小业务闭环是：

1. 浏览商品
2. 查看详情
3. 收藏 / 想要
4. 发起沟通
5. 创建订单
6. 约定面交
7. 完成交易
8. 审核与治理

若后续重构破坏这条主链路，即使页面更美观，也视为退化。

## 5. 角色边界

系统长期只保留三类角色语义：

- 游客
- 普通用户
- 管理员

当前角色约束：

### 5.1 游客

- 可浏览首页和商品详情
- 不可发布、发消息、下单
- 可有轻量本地偏好，但不可拥有正式交易能力

### 5.2 普通用户

- 同时具备买家和卖家能力
- 不拆成互斥角色体系
- 可发布、沟通、下单、收藏、评价

### 5.3 管理员

- 审核商品
- 处理举报
- 封禁 / 解封用户
- 查看治理与概览数据

## 6. 商品域边界

商品域长期必须保留以下核心语义：

- 标题
- 主分类
- 成色
- 价格
- 描述
- 标签
- 媒体
- 状态
- 卖家信息

商品域的关键边界：

1. 主分类用于数据治理、推荐和统计
2. 标签用于运营表达和筛选
3. 商品状态必须可追踪
4. 商品发布必须经过规则校验与审核流

## 7. 首页体验边界

首页可以持续改版，但必须保留以下体验原则：

1. 默认态简洁，不平铺所有信息
2. 先浏览，再筛选，再深入
3. 分类是长期有效入口
4. 活动和推荐服务于浏览，不喧宾夺主
5. 商品流仍然是首页核心

## 8. 校园服务边界

校园服务继续保持为独立子模块，不混入普通商品主流。

它承接的是：

- 跑腿
- 代办代取
- 拼单
- 临时帮忙

这意味着：

- 普通商品分类不应再次吸收这些需求
- 首页和推荐主流不应把它与二手商品混排

## 9. 治理边界

本系统不是“只要能买卖就行”的产品，治理是核心能力之一。

后续重构时不可丢失以下治理语义：

- 实名状态
- 信用分
- 商品审核
- 举报处理
- 封禁与解除封禁
- 操作留痕

## 10. 推荐与解释性边界

推荐可以逐步增强，但当前必须保留可解释性：

- 同类
- 常看
- 想要过
- 信用好

换句话说，推荐结果不能变成完全不可解释的黑盒输出。

## 11. 数据与接口最低约束

后续任何实现都至少应能稳定表达这些对象：

- 商品
- 订单
- 会话
- 举报
- 用户行为
- 用户资料

它们之间的关系不应在 UI 改版时被打散或临时绕开。

## 12. 非功能基线

当前仍然有效的非功能要求：

- 前后端统一 TypeScript
- Docker 化可复现启动
- 数据规模可通过种子重建
- 页面默认态简洁
- 结构允许继续接入更完整的 JWT、Socket、对象存储与测试体系

## 13. 结论

对后续重构而言，这份需求基线的意义是：

- 不允许把产品做偏
- 不允许只重做视觉，不保业务闭环
- 不允许为了页面方便破坏治理和交易结构

后续所有大的结构和 UI 改动，都应先验证是否仍满足本文档的边界。
