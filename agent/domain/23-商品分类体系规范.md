# 商品分类体系规范

## 1. 目标

本规范用于冻结 SwapCampus 商品分类体系，解决以下长期问题：

- 首页分类入口、发布分类、推荐画像、审核规则口径不一致
- “毕业急出”“免费送”“宿舍白名单”这类运营词被错误当作主分类
- 旧种子数据、测试数据、消息演示数据混用历史分类名称

本规范约束的是 **商品主分类体系**。  
首页导购入口、活动专区、标签、筛选词、专题词允许变化，但不得再作为主分类直接落库。

## 2. 单一事实源

当前分类统一入口已经收敛到以下两个文件：

- 前端：`frontend/src/constants/productCategories.ts`
- 后端：`backend/src/modules/products/product-categories.ts`

后续所有页面、接口、种子、推荐、审核、统计都必须只依赖这两个入口，不允许在页面、服务、脚本中再次手写一套分类常量。

## 3. 分类层级定义

SwapCampus 的商品分类层级固定为三层语义：

1. 主分类：唯一、稳定、落库、参与推荐和统计
2. 标签：可多选、可运营调整、用于搜索和筛选
3. 导购入口：仅用于首页聚合展示，最终必须映射回“主分类 + 标签”

约束如下：

- 一个商品只能属于一个主分类
- 一个商品可以拥有多个标签
- 一个首页入口可以聚合多个主分类下的若干标签或关键词
- “活动词”“交易词”“场景词”不得进入主分类集合

## 4. 最终冻结主分类

主分类固定为以下 10 类，不再新增、拆分或重命名：

| 编号 | 主分类 | 分类编码 | 典型内容 | 明确不包含 |
| --- | --- | --- | --- | --- |
| 1 | 数码电子 | `DIGITAL` | 手机、平板、电脑、耳机、相机、键鼠、显示器、充电设备 | 课程资料、纯卡券 |
| 2 | 教材资料 | `BOOKS` | 教材、讲义、真题、笔记、考试资料、学习工具书 | 普通文具、数码设备 |
| 3 | 宿舍生活 | `DORM` | 收纳、床上用品、台灯、宿舍日用、小型合规生活电器 | 服饰、美妆、专业办公设备 |
| 4 | 鞋服箱包 | `FASHION` | 衣物、鞋靴、双肩包、帽子、饰品 | 美妆护肤、运动器械 |
| 5 | 运动出行 | `SPORTS` | 球拍、球鞋、护具、自行车、滑板、头盔、出行装备 | 普通服饰、乐器 |
| 6 | 美妆个护 | `BEAUTY` | 护肤品、化妆品、个护电器、香氛、洗护 | 普通宿舍日用品 |
| 7 | 办公文具 | `OFFICE` | 文具、打印设备、收纳文件、桌面办公工具 | 教材资料、纯数码娱乐设备 |
| 8 | 卡券票务 | `TICKETS` | 打印券、咖啡券、洗衣卡、电影票、月卡、代金券 | 实物商品 |
| 9 | 兴趣文娱 | `HOBBY` | 乐器、桌游、动漫周边、手办、漫画、收藏类物品 | 主出行装备、纯学习资料 |
| 10 | 其他 | `OTHER` | 无法稳定归入前 9 类但允许发布的边缘类目 | 违规商品、校园服务任务 |

冻结规则：

- 数据库 `Product.category` 最终只允许出现以上 10 个中文名称之一
- `分类编码` 仅作为文档和未来枚举设计参考，当前代码中不强制落库
- UI 文案可调整，但主分类集合不可调整

## 5. 分类边界与归属规则

为避免反复争议，按以下边界判定：

### 5.1 优先按商品“主要交易对象”归类

- 卖的是“教材本体”，归 `教材资料`
- 卖的是“学习工具设备”，如打印机、计算器、订书机，归 `办公文具`
- 卖的是“电脑/平板/耳机”等电子硬件，归 `数码电子`

### 5.2 套装商品按核心价值归类

- “考研资料 + 计算器”以资料为主，归 `教材资料`
- “宿舍台灯 + 收纳盒”以宿舍用品为主，归 `宿舍生活`
- “键盘 + 鼠标 + 显示器支架”以外设为主，归 `数码电子`

### 5.3 卡券永远不落到实物分类

- 洗衣卡、咖啡券、打印券、电影票、健身月卡一律归 `卡券票务`

### 5.4 交易方式不是分类

以下内容只能做标签，不能做分类：

- 免费送
- 交换
- 同校面交
- 今天可取
- 毕业急出

### 5.5 校园服务不是商品分类

以下需求统一走 `CampusServiceTask`，不进入 `Product.category`：

- 代取快递
- 跑腿
- 拼单带货
- 临时帮忙
- 代办

## 6. 不再视为主分类的内容

以下内容必须从分类语义中剥离：

| 原表达 | 正确归属 |
| --- | --- |
| 毕业急出 | 时效标签 / 活动标签 |
| 免费送 | 交易标签 |
| 交换免费 | 交易标签 |
| 宿舍白名单 | 合规标签 |
| 今天可取 | 时效标签 |
| 同校面交 | 交易标签 |
| 考研考证 | 场景标签 |
| 桌搭灯具 | 场景标签或关键词 |
| 通勤办公 | 场景标签 |

推荐标签分组：

- 交易标签：`免费送` `可交换` `同校面交`
- 时效标签：`今天可取` `急出`
- 活动标签：`毕业清仓`
- 合规标签：`宿舍白名单`
- 场景标签：`考研` `桌搭` `通勤`

## 7. 首页分类入口规范

首页展示的是 **导购入口**，不是数据库主分类表。

入口规范：

- 入口名称允许更贴近用户语言
- 入口可附带 `badge`
- 入口下可配置若干 `rows`
- 每个入口最终必须绑定一个主分类
- 每一行展示词只能作为搜索词、标签词、示例词，不能替代主分类

当前首页入口维护位置：

- `frontend/src/constants/productCategories.ts`

当前首页入口字段结构：

- `shortTitle`：主分类短标题，必须与主分类一一对应
- `title`：首页展示标题
- `badge`：运营角标
- `rows[].label`：分组标题
- `rows[].items[]`：示例关键词

强约束：

- `PRODUCT_CATEGORY_HOME_GROUPS.length` 必须与主分类数量一致
- `shortTitle` 必须落在主分类集合内
- 首页入口允许改排版、文案、关键词，但不允许绕开主分类集合另起新类目

## 8. 旧分类兼容映射

为兼容历史数据、旧脚本和消息演示数据，保留旧分类到新主分类的归一化映射：

| 旧分类 | 新主分类 |
| --- | --- |
| 数码 | 数码电子 |
| 教材 | 教材资料 |
| 考研资料 | 教材资料 |
| 生活用品 | 宿舍生活 |
| 宿舍好物 | 宿舍生活 |
| 小家电 | 宿舍生活 |
| 鞋服 | 鞋服箱包 |
| 运动器材 | 运动出行 |
| 自行车 | 运动出行 |
| 文具 | 办公文具 |

兼容规则：

- 读取历史数据时统一 `normalize`
- 新发布商品必须直接写入新主分类
- 旧映射只用于兼容，不是新的业务口径
- 兼容映射命中失败时，默认回落到 `其他`

## 9. 当前代码落点

### 前端

- `frontend/src/constants/productCategories.ts`
  - 主分类常量
  - 历史分类映射
  - 首页入口定义
- `frontend/src/pages/ProductPublishPage.tsx`
  - 发布分类下拉读取主分类常量
- `frontend/src/utils/productCover.ts`
  - 商品封面主题按归一化主分类处理

### 后端

- `backend/src/modules/products/product-categories.ts`
  - 主分类常量
  - 历史分类映射
  - `normalizeProductCategoryName()`
- `backend/src/modules/products/products.service.ts`
  - 发布时归一化分类
  - 推荐和详情读取时统一分类
- `backend/src/modules/products/dto/create-product.dto.ts`
  - 当前仍是 `category: string`，依赖服务层归一化和校验

## 10. 数据与迁移要求

后续必须继续推进以下事项，直到分类真正稳定：

1. 将历史 `Product.category` 数据全量迁移为新主分类
2. 种子数据、消息演示数据、测试数据全部改写为新主分类
3. 推荐画像只保留主分类命中，不再持久化历史分类别名
4. 将标签系统独立定义，避免再次把交易词混回分类
5. 后续若要枚举化数据库字段，优先新增 `categoryCode` 或将 `category` 收敛为枚举

## 11. 评审与变更门槛

本规范冻结后，分类变更只能按以下门槛处理：

1. 不允许直接新增第 11 个主分类
2. 新需求优先落到标签、筛选项、专题活动或首页入口
3. 若必须改主分类，必须同时评审：
   - 数据库结构
   - 种子与迁移脚本
   - 前后端常量
   - 推荐逻辑
   - 审核规则
   - 埋点与统计口径

## 12. 结论

对于 SwapCampus，分类体系的最终口径应当是：

- 主分类固定 10 类
- 标签承接运营表达
- 首页入口承接导购表达
- 校园服务单独建模
- 所有实现只从统一常量入口读取

这套规则冻结后，后续 UI 可以大改，但数据骨架不再漂移。
